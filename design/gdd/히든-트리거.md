# 히든 트리거 (Hidden Trigger)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 발견의 기쁨
> **Creative Director Review**: Skipped — Lean 모드

## Overview

히든 트리거 시스템은 히든방 진입 이벤트를 수신하고 조건을 평가해 동료 발견 또는 대체 결과를 결정하는 Feature 레이어 시스템이다. #2 랜덤 던전이 생성한 방 데이터에는 각 히든방마다 `companion_id`가 사전 할당되어 있으며, 이 시스템은 해당 동료의 해금 여부를 #14 영구 진행에 조회한 뒤 결과를 발신한다. 미해금이면 #3 동료 해금에 이벤트를 전달하고, 이미 해금된 경우 MVP에서는 "이미 동료가 되어 있어요" 플레이버 텍스트로 처리한다. 이 시스템은 조건 평가와 이벤트 발신만 담당한다 — 해금 저장은 #14, 연출은 #3 소유.

## Player Fantasy

히든방 문을 열었을 때 새 동료 카드가 나타나는 순간. 또는 "아, 이 동료는 이미 해금했구나"라는 확인 순간 — 양쪽 모두 발견의 결과다.

## Detailed Rules

### 히든방 데이터 구조

`#2 랜덤 던전`이 생성하는 방 데이터는 `type`만 결정한다. `companion_id`는 **이 시스템(#9)이 소유하고 배정**한다 (2026-07-26 리비전 — 구 버전은 "#2 소유"로 잘못 표기했으나, `#2 랜덤 던전`의 실제 문서 어디에도 이 배정 로직이 없었음. 동료 ID 배정은 "어떤 동료인가"라는 정체성 문제라 방 지오메트리를 다루는 #2보다 #9의 소관에 더 가깝다):

```gdscript
# RoomData (랜덤 던전이 type만 생성; companion_id는 #9가 배정)
{
  "type": "hidden"
  # companion_id는 여기 없음 — #9.get_next_companion_id() 호출로 지연 배정 (아래 참조)
}
```

**동료 ID 배정 (2026-07-26 리비전 — #9 소유로 확정, 이미 작성돼 있던 알고리즘을 실제 소유자에게 재배치):**
- MVP 히든 동료 ID 풀: `["hidden_mage_02", "hidden_archer_03", "hidden_healer_04"]`
- 런 시작 시(rng 주입받아) 셔플 후 순서대로 히든방에 배정 (런당 최대 3개 히든방이므로 풀 초과 없음)
- `#2 랜덤 던전`은 히든방 생성 시 `HiddenTrigger.get_next_companion_id()`를 호출해 배정받는다 — `#2` 문서에는 이 호출 한 줄만 교차 참조로 추가하면 됨(별도 리뷰 재오픈 불필요, 텍스트 한 줄).

### 트리거 흐름 (2026-07-28 리비전 — 실제 진입 트리거 소유권 재정정)

```
히든방 진입 (#13 런 상태 관리가 advance_room()/advance_floor()로 방을 이동시킬 때마다 room_entered(room_data) 신호를 발신 — 2026-07-26 버전은 이 트리거를 "#2가 호출"이라 서술했으나, #2는 런 시작 시 방 데이터를 미리 생성만 할 뿐 런타임 이동 이벤트를 소유하지 않음. 실제 "현재 방이 바뀌었다"는 런타임 이벤트는 advance_room()/advance_floor()를 소유한 #13에서만 발생 가능 — 2026-07-28 교차 리뷰에서 발견 및 수정)
  ↓
이 시스템이 room_entered 신호를 구독 — room_data.type != "hidden"이면 무시
  ↓
room_data.type == "hidden"이면 HiddenTrigger.evaluate(room_data) 호출 (자체 호출, #13은 이 시스템의 존재를 모름 — Core→Feature 방향으로만 의존)
  ↓
ProgressManager.is_unlocked(room_data.companion_id) 조회
  ├─ false (미해금): emit companion_discovered(companion_id)
  │     → #3 동료 해금이 수신 및 처리
  └─ true (이미 해금): emit hidden_room_already_cleared(companion_id)
        → #20 UI/HUD가 수신 → 플레이버 텍스트 "이미 동료가 되어 있어요" 표시
        → `#4 장비`의 기존 드롭 로직을 그대로 호출해 장비 1개 지급 (2026-07-26 추가 — 아래 참조, 새 자원 시스템 도입 없이 이미 있는 장비 드롭 메커니즘 재사용)
```

### 핵심 API

| 신호/메서드 | 발신 조건 | 수신자 |
|-------------|-----------|--------|
| `get_next_companion_id()` | `#2`가 히든방 생성 시 호출 | #2 랜덤 던전 |
| `companion_discovered(id)` | 미해금 동료의 히든방 진입 | #3 동료 해금 |
| `hidden_room_already_cleared(id)` | 이미 해금된 동료의 히든방 진입 | #20 UI/HUD |

### Core Rules

1. **조건 평가만 담당**: 해금 처리는 #3, 저장은 #14. 이 시스템은 "어느 경로로 갈지"만 결정.
2. **companion_id 유효성 검증**: #10 동료 데이터에 해당 id가 없으면 `push_warning` 후 `hidden_room_already_cleared` 발신 (빈 방으로 처리, 게임 진행 블록하지 않음).
3. **대체 결과에도 보상 포함 (2026-07-26 리비전)**: 이미 해금된 경우 플레이버 텍스트 + `#4 장비`의 기존 드롭 로직 재사용(장비 1개 지급). 구 버전은 "장비 드롭 없음, Full Vision에서 추가"였으나, MVP 히든 동료 풀이 3개뿐이라 몇 런 안에 소진되면 이후 모든 히든방이 영구적으로 빈 보상이 되는 문제가 리뷰에서 확인됨 — 새 시스템 도입 없이 이미 존재하는 #4 드롭 메커니즘을 재사용하는 것으로 지금 해결.

## Formulas

수치 공식 없음. 조건 분기:

```
is_unlocked(companion_id) == false → companion_discovered 발신
is_unlocked(companion_id) == true  → hidden_room_already_cleared 발신
```

## Edge Cases

- **companion_id가 #10 데이터에 없음**: 유효하지 않은 ID → `push_warning("Unknown companion_id: [id]")` + `hidden_room_already_cleared` 발신 (조용히 빈 방 처리, 게임 진행 블록하지 않음).

- **같은 런에서 같은 companion_id 히든방을 두 번 진입**: 이 시스템 자신이 `get_next_companion_id()`에서 셔플된 풀을 순서대로 소진하며 배정하므로(위 참조), 런당 최대 히든방 수(3개)가 풀 크기(3개)를 넘지 않는 한 같은 id가 중복 배정될 수 없다 — 2026-07-26 리비전: 구 버전은 이 보장을 "#2 책임"으로 돌렸으나 배정 로직 자체가 #9 소유로 정정됨에 따라 이 시스템이 직접 보장. 혹시 발생하더라도 두 번째 진입 시 `RunManager.discovered_companions`에 이미 포함 → `is_unlocked`와 무관하게 #3가 중복 해금 방지(2중 방어).

- **히든방 진입 후 앱 종료**: RunManager 상태가 로컬 세이브로 복구되지 않는 MVP에서 히든 트리거 이벤트는 재발신되지 않는다. 해금이 `#14.commit_run_end()`(런 종료 시)까지 도달했다면 저장 완료 — 도달 전 종료 시 소실 (허용 가능한 엣지 케이스; 2026-07-26 리비전: 구 버전이 참조한 `unlock_companion()`은 #14 리비전으로 런 종료 경로에서 더 이상 쓰이지 않음).

## Dependencies

### Upstream Dependencies

| 시스템 | 의존 유형 | 사용 |
|--------|-----------|------|
| #2 랜덤 던전 | **Soft** (2026-07-28 리비전 — 범위 축소, 아래 참조) | 히든방 생성 시 `get_next_companion_id()` 호출만 받음 — 런타임 진입 트리거는 아래 `#13` 소관 |
| #13 런 상태 관리 | **Hard** (2026-07-28 추가 — 실제 room-entry 트리거 소유자로 정정) | `room_entered(room_data)` 신호 구독 — `advance_room()`/`advance_floor()`가 방을 옮길 때마다 발신, `room_data.type=="hidden"`이면 이 시스템이 자신의 `evaluate()`를 호출 |
| #10 동료 데이터 | **Soft** | companion_id 유효성 검증 |
| #14 영구 진행 | **Hard** | `is_unlocked(companion_id)` 조회 |

## Tuning Knobs

## Visual/Audio Requirements

이 시스템은 시각/오디오 자산을 소유하지 않는다. 신호를 발신하면:
- `companion_discovered` → #3 동료 해금이 발견 연출 처리
- `hidden_room_already_cleared` → #20 UI/HUD가 텍스트 팝업 표시

## UI Requirements

이 시스템은 UI를 소유하지 않는다. "이미 동료가 되어 있어요" 텍스트 팝업은 `#20 UI/HUD` 소유.

## Acceptance Criteria

1. (미해금 동료 발견) GIVEN `is_unlocked("hidden_archer_03") == false` WHEN 해당 companion_id를 가진 히든방에 진입하면 THEN `companion_discovered("hidden_archer_03")` 신호가 발신된다.

2. (이미 해금 처리) GIVEN `is_unlocked("hidden_mage_02") == true` WHEN 해당 companion_id를 가진 히든방에 진입하면 THEN `hidden_room_already_cleared("hidden_mage_02")` 신호가 발신되고 `companion_discovered`는 발신되지 않는다.

3. (유효하지 않은 ID) GIVEN `companion_id = "존재하지않는ID"` WHEN 히든방에 진입하면 THEN `push_warning`이 기록되고 `hidden_room_already_cleared`가 발신된다.

4. (이미 해금 시 장비 드롭, 2026-07-26 추가) GIVEN `is_unlocked("hidden_mage_02") == true`인 상태에서 WHEN 해당 히든방에 진입하면 THEN `hidden_room_already_cleared` 신호와 함께 `#4 장비`의 드롭 로직이 호출되어 장비 1개가 지급된다.

5. (동료 ID 배정 순서, 2026-07-26 추가) GIVEN 셔플된 풀 `[A, B, C]`에서 `get_next_companion_id()`가 아직 호출되지 않은 상태에서 WHEN 히든방 3개가 순서대로 생성되며 각각 호출하면 THEN A, B, C가 정확히 한 번씩, 셔플 순서대로 반환되고 4번째 호출은 발생하지 않는다(런당 최대 히든방 3개).

6. (room_entered 구독 — 히든방, 2026-07-28 추가 — 트리거 소유권 명시) GIVEN `#13`이 `room_entered(room_data)`를 발신하고 `room_data.type == "hidden"`인 상태에서 WHEN 이 시스템이 해당 신호를 수신하면 THEN `evaluate(room_data)`가 호출된다.

7. (room_entered 구독 — 비히든방 무시, 2026-07-28 추가) GIVEN `#13`이 `room_entered(room_data)`를 발신하고 `room_data.type == "combat"`인 상태에서 WHEN 이 시스템이 해당 신호를 수신하면 THEN `evaluate()`가 호출되지 않는다.

(구 AC4 "companion_discovered 수신자 연동"은 삭제됨 — 2026-07-26 리비전. #3의 내부 동작을 검증하는 AC였고, 신호가 올바른 id로 발신되는지는 AC1이 이미 검증한다.)

(구 AC5 "전투 중 미발동"도 삭제됨 — 이 시스템의 흐름은 히든방 진입 이벤트 자체로부터 시작되므로, 그 이벤트가 전투 중 발생하지 않는다는 보장은 전적으로 `#2`/`#13`의 몫이며 이 시스템이 검증할 코드 경로가 없다.)

(구 AC6 "런 내 중복 방지"도 삭제됨 — THEN 절이 전부 `#3`의 Core Rule이었고, 이 시스템은 자체 중복 검사 로직을 갖지 않는다.)
