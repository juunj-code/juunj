# 런 상태 관리 (Run State Management)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 성장은 영원하다 (런 생명주기를 통해 발견된 동료가 #14로 전달됨)
> **Creative Director Review**: Skipped — Lean 모드

## Overview

런 상태 관리 시스템은 단일 런(시작 → 던전 탐험 → 종료)의 모든 **동적 상태**를 소유하는 Core 레이어 런타임 컨테이너다. 파티 편성 완료 시 생성되어 런 종료까지 유지되며, 현재 층수·방 위치·파티원 런타임 스탯(현재 HP/SP/상태이상)·이번 런에서 발견한 동료 목록 등 "런 중에 변하는 모든 것"을 소유한다. Godot Autoload 싱글톤(`RunManager`)으로 구현해 어느 씬에서도 접근 가능하게 한다. 이 시스템은 "게임 로직"을 실행하지 않는다 — 전투 공식(#6)·적 AI(#7)·상태이상(#12)·영구 진행(#14)이 각자의 로직을 실행할 때 여기서 상태를 읽고 결과를 여기에 쓴다. 런이 종료되면 이 시스템이 수집한 "이번 런 발견 동료 목록"을 #14 영구 진행에 넘기고 상태를 초기화한다.

## Player Fantasy

플레이어는 "런 상태 관리"를 보지 않는다. 하지만 이 시스템이 없으면:
- 전투에서 이긴 후 다시 던전 화면으로 돌아올 때 HP가 전투 전 값으로 돌아와 있다.
- 어떤 층에 있었는지 기억이 없어 같은 층을 무한 반복한다.
- 런 종료 후 "발견한 동료" 목록이 없어 영구 해금이 안 된다.

이 시스템이 완벽히 동작할 때 플레이어가 느끼는 것: "내가 3층에서 HP 40으로 전투에 들어갔고, 이겼고, HP 20이 남았다"는 연속된 경험. 런의 연속성이 곧 이 시스템이 제공하는 가치다.

## Detailed Rules

### 런 생명주기

```
IDLE ──(파티 선택 완료)──→ EXPLORING
EXPLORING ──(전투 방 진입)──→ IN_COMBAT
IN_COMBAT ──(전투 승리)──→ EXPLORING
IN_COMBAT ──(전멸)──→ RUN_ENDED (실패)
EXPLORING ──(보스 처치)──→ RUN_ENDED (성공)
RUN_ENDED ──(#14 영구 진행 전달 완료)──→ IDLE
```

### RunManager Autoload 소유 데이터

```gdscript
# 런 메타
var state: String = "IDLE"      # "IDLE" | "EXPLORING" | "IN_COMBAT" | "RUN_ENDED"
var current_floor: int = 0      # 1-based (1층~N층)
var is_success: bool = false     # RUN_ENDED 시 성공 여부

# 파티 런타임 상태 (2026-07-26 리비전: private + guarded getter — Core Rule 2의
# IDLE 접근 차단은 bare public var로는 강제 불가능하므로, 프로퍼티 getter로 구현)
var _party: Array[CompanionRunState] = []
var party: Array[CompanionRunState]:
	get:
		if state == "IDLE":
			push_error("RunManager.party accessed while state=IDLE")
			return []
		return _party

# 현재 전투 적 런타임 상태 (전투 중에만 유효) — party와 동일한 가드 패턴
var _current_enemies: Array[EnemyRunState] = []
var current_enemies: Array[EnemyRunState]:
	get:
		if state == "IDLE":
			push_error("RunManager.current_enemies accessed while state=IDLE")
			return []
		return _current_enemies

# 이번 런 수집 데이터 (#14 영구 진행으로 전달)
var discovered_companions: Array[String] = []  # companion id 목록
```

### CompanionRunState (런타임 동료 상태)

```gdscript
class_name CompanionRunState

var companion_id: String         # CompanionData 참조
var current_hp: int              # 현재 HP (0이면 전투 불가)
var current_sp: int = 0          # 현재 SP
var active_effects: Array[StatusEffect]  # StatusEffect 인스턴스 목록 (#12 소유)
var weapon_slot: String = ""     # equipment_id, "" = 빈 슬롯 (#4 장비 소유, 2026-07-26 추가)
var armor_slot: String = ""      # 동일 (#4 장비 소유)
```

### EnemyRunState (런타임 적 상태)

```gdscript
class_name EnemyRunState

var enemy_id: String             # EnemyData 참조
var current_hp: int              # 현재 HP
var current_sp: int = 0          # 현재 SP
var active_effects: Array[StatusEffect]  # StatusEffect 인스턴스 목록 (#12 소유)
```

### Signals (2026-07-26 추가 — 리뷰에서 발견된 미정의 갭)

`#20 UI/HUD`를 비롯한 9개 이상의 다운스트림 시스템이 이 시스템의 상태 변화를 폴링이 아닌 이벤트로 구독해야 하므로, 아래 시그널을 RunManager가 발신한다:

```gdscript
signal floor_changed(new_floor: int)
signal combat_entered(enemies: Array[EnemyRunState])
signal combat_exited(victory: bool)
signal run_ended(success: bool)
signal state_changed(old_state: String, new_state: String)
```

### 런 시작 절차

1. `#15 파티 구성`이 선택한 companion_id 목록 수신
2. 각 CompanionData 로드 → `CompanionRunState` 생성 (`current_hp = base_hp`, `current_sp = 0`)
3. `current_floor = 1`, `state = "EXPLORING"`, `discovered_companions = []`
4. `#19 씬 관리`를 통해 DungeonScreen 전환

### 런 종료 절차 (`end_run(success: bool)`)

**2026-07-26 리비전 — 멱등성 보장**: `end_run()`은 `state == "RUN_ENDED"`이면 즉시 no-op으로 반환한다(이미 종료 처리된 런에 다시 진입하지 않음 — 중복 호출로 인한 #14 이중 전달 방지).

1. `state != "RUN_ENDED"` 확인 (아니면 즉시 반환)
2. `state = "RUN_ENDED"`, `is_success = 승리여부`
3. `discovered_companions` → `#14 영구 진행` 전달 (해금 처리)
4. `#19 씬 관리`를 통해 RunResultScreen 전환
5. RunResult 화면 완료 후 → `reset()` 호출

### `reset()` (2026-07-26 리비전 — 전체 필드 명시)

```
_party.clear()
_current_enemies.clear()
discovered_companions.clear()
current_floor = 0
is_success = false
state = "IDLE"
```

### 전투 진입/종료

```
전투 진입:
  _current_enemies = [EnemyRunState(enemy_id, base_hp, sp=0) for each enemy in room]
  state = "IN_COMBAT"
  SceneManager.go_to(S-05 BattleScreen, FADE)

전투 종료 (승리):
  _current_enemies.clear()
  state = "EXPLORING"
  SceneManager.go_to(S-04 DungeonScreen, FADE)

전투 종료 (전멸, 2026-07-26 리비전 — 소유권 명확화):
  이 시스템은 자체적으로 전멸을 판정하지 않는다. `#1 턴제 전투`가 `#6 전투 공식` Formula ⑤로
  판정한 결과(defeat)를 받으면 RunManager.end_run(success=false)를 호출한다.
  (DOT로 인한 전멸도 동일 경로: #12 DOT 틱 → #1이 #6 Formula ⑤ 호출 → defeat 시 #1이 end_run() 호출.
  이 시스템이 자체 all(hp<=0) 체크를 별도로 수행하지 않는다 — 판정 로직의 단일 소유자는 #6뿐이다.)
```

### Core Rules

1. **단일 진실 공급원**: 파티원 현재 HP·SP·상태이상은 반드시 여기(`CompanionRunState`)에 저장. 다른 시스템은 여기서 읽고 쓴다. 로컬 복사본 유지 금지. 승패 판정 로직 자체도 이 원칙을 따른다 — `#6 전투 공식` Formula ⑤가 유일한 소유자이며, 이 시스템은 그 결과(`end_run()` 호출)만 받는다(전투 종료 절차 참조).
2. **런 바깥/종료 후 접근 차단**: `state == "IDLE"` **또는 `state == "RUN_ENDED"`** 상태에서 party/current_enemies 접근 시 `push_error` + 빈 값 반환(`party`/`current_enemies` 프로퍼티 getter로 구현 — RunManager 소유 데이터 섹션 참조). RUN_ENDED는 RunResultScreen이 표시되는 동안 지속되는 실질적 대기 상태이므로 IDLE과 동일하게 가드한다 — 이 창 동안의 `advance_floor()`/`add_discovered_companion()` 등 상태 변경 호출도 동일하게 `push_error` + no-op 처리한다(`end_run()`은 예외적으로 멱등이므로 별도 처리, 전투 종료 절차 참조).
3. **discovered_companions 중복 없음**: `add_discovered_companion(id)` 호출 시 이미 존재하는 id면 추가하지 않음.
4. **층수는 RunManager만 변경**: `advance_floor()`를 통해서만 `current_floor += 1`. 직접 대입 금지.

## Formulas

이 시스템은 수치 공식을 소유하지 않는다. 상태를 읽고 쓰는 컨테이너이며, 아래 초기화 값이 이 시스템의 "공식"이다.

| 값 | 초기화 시점 | 초기값 |
|----|-------------|--------|
| `companion.current_hp` | 런 시작 | `CompanionData.base_hp` |
| `companion.current_sp` | 런 시작 / 전투 시작 | 0 |
| `companion.active_effects` | 런 시작 / 전투 종료 | `[]` |
| `enemy.current_hp` | 전투 진입 | `EnemyData.base_hp` |
| `enemy.current_sp` | 전투 진입 | 0 |
| `enemy.active_effects` | 전투 진입 | `[]` |
| `current_floor` | 런 시작 | 1 |
| `discovered_companions` | 런 시작 | `[]` |

**층간 HP 유지**: 전투 종료 후 파티원 `current_hp`는 전투 결과값 그대로 유지 — 다음 방에 체력이 깎인 채로 진입한다. 회복은 "휴식 방" 이벤트가 처리 (YAGNI: 아직 설계 없음, MVP에서는 전투 후 HP 회복 없음).

## Edge Cases

- **런 중 브라우저 강제 종료/탭 닫기**: 런 상태는 메모리에만 존재 — 소실됨. MVP에서는 의도적 설계. "발견한 동료"는 런 종료(#14 영구 진행 전달) 이후에만 저장되므로, 종료 전 소실은 해당 런 발견 동료를 잃는다. 필라 2("성장은 영원하다")와 충돌하나, MVP에서는 허용 — 클라우드 세이브(#5)가 Full Vision에서 해결.

- **전투 중 씬 전환 인터럽트**: 정상 흐름에서 발생하지 않아야 함. 발생 시(버그) state=IN_COMBAT으로 고착 — 다음 씬 전환 요청 시 `state != "EXPLORING"` 감지 후 `push_error` + **`state = "EXPLORING"`으로 강제 복구** (2026-07-26 리비전: 복구 대상 값 명시).

- **파티 전원 HP=0 (전멸) 판정 타이밍, 2026-07-26 리비전 — 소유권 재정리**: DOT 데미지로 마지막 동료가 사망하는 경우 포함. 이 시스템은 `all(hp<=0)` 판정을 자체 수행하지 않는다 — `#6 전투 공식` Formula ⑤가 유일한 판정 소유자이며, `#1 턴제 전투`가 DOT 틱 처리 후 Formula ⑤ 호출을 트리거한다. RunManager는 그 결과로 `end_run(success=false)` 호출만 받는다(런 종료 절차 참조). (구 버전은 "#12가 RunManager에 위임해 RunManager가 자체 판정"이라고 서술했으나, 이는 `#6`/`#12` 문서와 불일치하는 중복 구현이었음 — 수정됨.)

- **`advance_floor()` 호출 시 이미 최대 층수**: MVP는 3층 고정. 3층 보스 처치 후 `advance_floor()` 대신 `end_run(success=true)` 호출. 최대 층수 초과 호출은 `push_error`.

- **같은 런에서 이미 해금된 동료 재발견**: `add_discovered_companion(id)` 내부에서 중복 체크 — `discovered_companions`에 추가 안 함. #3 동료 해금·#14 영구 진행이 처리.

## Acceptance Criteria

1. (런 시작) GIVEN 파티 [A, B, C]가 선택된 상태에서 WHEN RunManager.start_run([A,B,C])가 호출되면 THEN party에 3개 CompanionRunState가 생성되고, 각각 current_hp=base_hp·current_sp=0·active_effects=[]이며, current_floor=1·state="EXPLORING"이다.

2. (HP 유지) GIVEN 전투 후 동료 A의 current_hp=40인 상태에서 WHEN 전투 종료 후 DungeonScreen으로 전환되면 THEN party에서 A의 current_hp는 여전히 40이다.

3. (전투 진입) GIVEN state="EXPLORING"인 상태에서 WHEN 전투 방에 진입하면 THEN current_enemies가 해당 방 적들의 EnemyRunState로 채워지고 state="IN_COMBAT"이 된다.

4. (전투 승리) GIVEN state="IN_COMBAT"이고 모든 적 HP=0인 상태에서 WHEN 전투 종료 처리가 실행되면 THEN current_enemies=[]이고 state="EXPLORING"으로 복귀한다.

5. (전멸) GIVEN 모든 동료 current_hp=0이고 `#1 턴제 전투`가 `#6 전투 공식` Formula ⑤로 defeat을 판정한 상태에서 WHEN `RunManager.end_run(success=false)`가 호출되면 THEN state="RUN_ENDED"·is_success=false가 된다. (판정 자체는 이 시스템의 대상이 아니다 — `#6`의 AC 범위.)

6. (층 진행) GIVEN current_floor=1인 상태에서 WHEN advance_floor()가 호출되면 THEN current_floor=2가 된다.

7. (동료 발견) GIVEN discovered_companions=[]인 상태에서 WHEN add_discovered_companion("hidden_mage_02")가 두 번 호출되면 THEN discovered_companions=["hidden_mage_02"] (중복 없음).

8. (런 종료 → 영구 진행 핸드오프, 2026-07-26 재작성 — Logic/Integration 분리) GIVEN discovered_companions=["hidden_mage_02"]인 상태에서 WHEN end_run()이 실행되면 THEN `#14 영구 진행`의 해금 처리 인터페이스가 `["hidden_mage_02"]` 인자로 호출된다(#14는 mock/stub — 이 AC는 #13이 올바른 인자로 호출하는지만 검증하는 Integration 테스트이며, #14의 실제 해금 로직은 검증하지 않는다).
