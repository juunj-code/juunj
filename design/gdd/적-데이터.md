> **Creative Director Review (CD-GDD-ALIGN)**: Skipped — Lean 모드

## Overview

적 데이터 시스템은 바람의 탑 게임 내 모든 적(Enemy)의 **정적 블루프린트**를 정의하는 Foundation 레이어 시스템이다. 각 적의 이름·스탯(HP/공격력/방어력/속도)·스킬 참조·처치 시 보상(경험치 등) 같은 "전투마다 변하지 않는 고정 정보"를 담은 데이터 구조체이며, #1 턴제 전투·#6 전투 공식·#7 적 AI 3개 시스템의 공통 기반으로 동작한다. 적의 행동 패턴(공격적/방어적 같은 AI 로직)은 이 시스템이 아닌 #7 적 AI가 소유하며, 전투 중 동적 상태(현재 HP 등)는 #13 런 상태 관리가 소유한다. 이 시스템은 #10 동료 데이터와 함께 전투 밸런스의 기준점 역할을 하며, 동료 스탯 범위(base_hp 60~150 등)와 대비되는 적 스탯 범위를 확정해 #6 전투 공식이 참조할 입력값을 제공한다. MVP에서는 3층 던전에 등장할 일반 적 3종 + 보스 1종을 정의한다.

## Player Fantasy

플레이어는 "적 데이터 시스템"을 인식하지 않는다. 대신 전투 한 판 한 판에서 "이 적, 패턴이 읽힌다"는 감각과 "졌다면 내 실수지, 불공정한 게 아니다"는 신뢰를 경험한다.

적 데이터 시스템이 만드는 감각:
- **읽히는 위협**: 적의 스탯이 명확한 역할(빠르고 약한 놈 / 느리고 단단한 놈)을 가져서, 플레이어가 한두 턴 안에 "이 녀석부터 잡아야겠다"는 판단을 내릴 수 있다.
- **공정한 도전**: 필라 3(솔로도 최강)을 뒷받침 — 어떤 적도 파티 구성과 전략으로 극복 가능해야 하며, 무작위 즉사나 회피 불가능한 패턴은 없다.
- **보스의 짜릿함**: 일반 적과 확연히 다른 스탯 곡선(더 높은 HP, 더 위협적인 스킬)으로 "이건 진짜 보스다"가 스탯만 봐도 체감된다.

플레이어는 데이터 구조를 경험하지 않는다. 전투 중 "이 적 패턴을 파악했다"는 성취감과, 죽었을 때 "내가 준비가 부족했다"는 납득을 경험한다.

## Detailed Rules

### Core Rules

**EnemyData 스키마** (GDScript — `EnemyData extends Resource`):

```gdscript
class_name EnemyData
extends Resource

# 식별자
@export var id: String            # 고유 ID (예: "goblin_01", "boss_wind_guardian")
@export var name: String          # 표시 이름 (예: "고블린 정찰병")

# 시각
@export var sprite_id: String     # 전투 스프라이트 ID

# 기본 스탯 (전투마다 고정)
@export var base_hp: int    # 기본 최대 HP — 범위 25~65(일반)/150~300(보스), 단 0 이하는 로드 자체를 거부 (Edge Cases 참조)
@export var base_atk: int   # 기본 공격력
@export var base_def: int   # 기본 방어력
@export var base_spd: int   # 기본 속도 (턴 순서 결정)

# 스킬
@export var skill_id: String  # SkillData 리소스 참조 ID (MVP: 정확히 1개, 보스도 동일). 참조하는 SkillData의 damage_multiplier는 0.5~1.4 (Formulas 참조)

# 등급
@export var is_boss: bool = false  # true = 보스 — 스탯 곡선 상향 + 전투 UI 특수 표시
```

**파일 위치 및 로딩 소유권:** `assets/data/enemies/[id].tres`

로딩·중복 검증·정렬은 `EnemyRegistry` 오토로드가 소유한다 (`#10 동료 데이터`의 `CompanionRegistry`와 동일하게, 이 GDD는 데이터 계약만 정의하고 구현은 별도 구현 GDD/ADR에서 상세화). `EnemyRegistry`는 `CompanionRegistry`와 동일한 로직(폴더 열거 → 파일명 오름차순 정렬 → 로드 → `id` 중복 검사)을 공용 유틸리티 함수로 공유한다 — 폴더 경로와 대상 타입만 다른 얇은 wrapper이며, 로직을 두 곳에 중복 구현하지 않는다.

`skill_id`는 #10 동료 데이터가 정의한 `SkillData` 리소스를 그대로 재사용한다 (별도 EnemySkillData 없음 — 스킬 스키마는 동료/적 공통). 단, EnemyData가 참조하는 SkillData는 **`target_type="enemy"`만 사용**하고 `damage_multiplier`는 전역 범위(0.5~3.0)보다 좁은 **0.5~1.4**를 따른다 (Formulas 섹션의 즉사 방지 검증 참조 — 공용 스키마이지만 적 측 스킬에는 이 문서가 추가 제약을 건다).

### States and Transitions

적 데이터 자체는 **불변(immutable)** — 상태 전이 없음. 적 라이프사이클은 다른 시스템이 관리:

| 상태 | 관리 시스템 | 설명 |
|------|-------------|------|
| 스폰 대기 | #2 랜덤 던전 | 어느 방에 어떤 적을 배치할지 결정 |
| 전투 중 | #13 런 상태 관리 | 현재 HP, 상태이상 — 이 시스템은 소유하지 않음 |
| 처치됨 | #1 턴제 전투 | 전투 종료 판정에 반영. 동료와 달리 영속 저장 없음 (적은 해금 개념 없음) |

## Formulas

이 시스템은 계산 공식이 없는 순수 데이터 시스템이다. 대신 #6 전투 공식이 입력값으로 사용할 **적 스탯 범위**를 여기서 확정한다. 범위는 #10 동료 데이터가 정의한 스탯 범위(base_hp 60~150, base_atk 10~30, base_def 5~20, base_spd 1~10)를 기준점으로 삼아, "그룹전(적 1~3마리)에서 즉사 없이, 보스는 격이 다르게" 원칙으로 산정했다.

**스탯 범위 정의:**

| 스탯 | 심볼 | 타입 | 일반 적 범위 | 보스 범위 | 설명 |
|------|------|------|--------------|-----------|------|
| 기본 최대 HP | `base_hp` | int | 25 ~ 65 | 150 ~ 300 | 일반 적은 동료 HP 최저치(60)보다 낮게 → 여러 마리가 빠르게 정리되는 리듬. 보스는 동료 HP 상한(150)을 하한선으로 → 1:1에서도 격이 다름을 체감 |
| 기본 공격력 | `base_atk` | int | 8 ~ 18 | 15 ~ 25 | 그룹 공격 시 동료 HP 최저치(60)의 절반을 넘지 않도록 상한을 눌러 즉사 방지 |
| 기본 방어력 | `base_def` | int | 3 ~ 12 | 8 ~ 20 | 일반 적은 낮게 → "때리는 맛". 보스 하한을 8로 낮춤(기존 10) — 솔로 밸런스 재검토(2026-08-02)에서 하한 10 이상이면 아이라 단독으로는 완전 결정론적 전투(크리티컬/회피 없음) 특성상 최적 플레이로도 이론상 승리 불가능함을 시뮬레이션으로 확인, `boss_balance_test.gd`로 회귀 고정 |
| 기본 속도 | `base_spd` | int | 1 ~ 9 | 4 ~ 9 | 보스는 하한을 4로 올려 매 턴 확실히 개입 (존재감 없는 보스 방지) |

**MVP 4종 예시 배분 (참고용 — 실제 밸런스는 프로토타입에서 검증):**

| 유형 | base_hp | base_atk | base_def | base_spd | 컨셉 |
|------|---------|----------|----------|----------|------|
| 일반 적 A (속도형) | 30 | 16 | 4 | 8 | 먼저 치고 빠지는 글래스 캐논 |
| 일반 적 B (밸런스형) | 45 | 13 | 7 | 5 | 무난한 표준 적, 기준점 역할 |
| 일반 적 C (탱커형) | 65 | 10 | 12 | 2 | 느리지만 오래 버팀 |
| 보스 | 150 | 15 | 8 | 6 | HP는 동료 상한급, ATK/DEF는 낮춰 지구전형 — 강제 솔로 첫 보스전에서도 최적 플레이로 승산 있음 (2026-08-02 재조정, 기존 220/20/16은 결정론적 전투에서 솔로 승리 불가능이었음) |

> 이 범위는 #6 전투 공식 GDD의 데미지 계산 입력 범위가 된다. 전투 공식 GDD 작성 전에 변경이 필요하면 이 GDD를 먼저 수정한다.

**즉사 방지 검증 (2026-07-26 리비전 — 기존 앵커가 `전투-공식.md`의 실제 공식 `damage = max(1, floor(atk * multiplier) - def)`으로 계산 시 이미 깨져 있음이 리뷰에서 확인됨):**

이전 앵커("적 ATK × 스킬 배율 − 동료 DEF 최저치(5)가 동료 HP 최저치(60)의 절반을 넘지 않는 선")는 보스 ATK 최댓값(25)에 `#10 동료 데이터`가 정의한 SkillData의 전역 `damage_multiplier` 상한(3.0)을 대입하면 `floor(25*3.0)-5 = 70` — 동료 HP 최저치(60) 전체를 넘는 완전 즉사가 계산상 나온다. `damage_multiplier`는 힐/버프 스킬(대상 아군)에도 쓰이는 **공용 SkillData 필드**라 전역 상한 자체를 낮출 수 없으므로, 대신 이 문서가 **적(Enemy)이 참조하는 SkillData에 한해** 더 좁은 유효 범위를 강제한다:

- **적 스킬(`target_type="enemy"`, 즉 EnemyData.skill_id가 참조하는 SkillData)의 `damage_multiplier` 유효 범위: 0.5 ~ 1.4** (전역 SkillData 범위 0.5~3.0보다 좁음 — 동료 측 스킬은 이 제약을 받지 않는다. 공정성 필라는 "적이 동료에게 주는 피해"에만 관여하므로 방향성 있는 비대칭 제약이다).
- **검증 앵커 (수정판)**: `floor(적_base_atk_최댓값 × damage_multiplier) − 동료_base_def_최저치(5) ≤ 30` (동료 HP 최저치 60의 절반). 보스 최댓값(25)과 상한 배율(1.4)로 계산: `floor(25×1.4)−5 = 35−5 = 30` — 정확히 경계값 충족. 일반 적 최댓값(18)으로는 `floor(18×1.4)−5 = 25−5 = 20`, 더 여유 있음.
- 이 범위 위반(적 스킬의 `damage_multiplier > 1.4`)은 빌드 검증 도구가 경고로 잡아야 한다(중복-id·skill_id 참조 무결성 검사와 동일한 도구, Acceptance Criteria 참조).
- **범위 밖 참고**: 3마리 동시 타겟 집중 공격 시나리오는 이 상한 안에서도 여전히 위험(아래 Edge Cases 참조)하며, 이는 의도된 것이다 — 단일 히트의 "불공정한 즉사"만 이 앵커가 막고, 다수 적의 집중 공격 완화는 `#7 적 AI`의 타겟 분산 규칙 책임으로 명시적으로 남긴다.

## Edge Cases

- **적 3마리가 모두 같은 파티원을 타겟팅하는 경우**: 동일한 공식(`floor(atk×multiplier)-def`, DEF는 매 히트마다 적용됨 — "완전 관통 가정"이 아니라 위 즉사 방지 앵커와 동일한 실제 공식 기준)으로 계산 시, 일반 적 ATK 상한(18)·배율 상한(1.4)·동료 DEF 최저치(5) 기준 히트당 `floor(18×1.4)-5=20`, 3마리 합산 시 60 — 동료 HP 최저치(60)와 정확히 같아 한 라운드에 전멸 가능한 경계 케이스다. 이 GDD는 스탯 범위만 소유하며 타겟팅 로직은 소유하지 않는다 — `#7 적 AI`는 **반드시** 타겟 분산 규칙(예: 동일 타겟 연속 지정 확률 감소, 또는 마리당 최대 1회 행동 제한)을 포함해야 하며, 이 제약은 `#7 적 AI` GDD 작성 시 확정한다. (단일 히트 즉사는 위 앵커가 막고, 다수-적 집중 공격 완화는 의도적으로 `#7`의 책임으로 남겨둔다.)

- **`base_hp`가 0 이하인 경우 (크래시 등급 — 클램핑/경고 대상 아님, 로드 거부 대상)**: `#10 동료 데이터`와 동일 원칙 — `base_hp ≤ 0`은 전투 시작 즉시 승패가 결정되는 게임 루프 크래시이지 밸런스 튜닝 범위 문제가 아니다. 로드 시 `push_error("Invalid base_hp for [id]: must be > 0")` 출력 후 **해당 EnemyData는 로드하지 않는다** (게임에 등록되지 않음).

- **같은 `id`를 가진 `.tres` 파일이 2개 이상 로드된 경우**: `EnemyRegistry`가 `assets/data/enemies/`의 파일 목록을 **파일명 오름차순으로 정렬한 뒤** 순서대로 로드한다 — "첫 번째로 로드된 데이터"는 이 정렬 순서 기준이며, 플랫폼(에디터/웹 익스포트)마다 달라지는 디렉토리 스캔 순서에 의존하지 않는다(`#10 동료 데이터`의 `CompanionRegistry`와 동일 규칙). 정렬 후 첫 번째가 아닌 나머지는 `push_error("Duplicate enemy id: [id]")` 출력 후 무시. 빌드 검증 도구가 이를 경고로 잡아야 한다(Acceptance Criteria 참조).

- **`skill_id`가 존재하지 않는 스킬을 참조하는 경우 (런타임 세이프티넷)**: 이 폴백 로직은 `#1 턴제 전투`가 소유한다 — 이 GDD는 데이터 계약만 명시: SkillData 로드 실패 감지 시 `skill_id = "skill_basic_attack"`(기본 공격)으로 fallback, `push_warning("Missing skill: [skill_id], falling back to basic_attack")` 로그 출력. 이와 별도로 빌드 검증 도구가 로드 이전에 `skill_id` 참조 무결성을 정적으로 검사한다(`#10 동료 데이터`와 동일 도구 재사용, 중복-id 검증과 함께 수행).

- **`sprite_id`가 비어 있거나 해당 스프라이트가 없는 경우**: fallback 스프라이트(`sprite_missing.png`) 사용. null 참조 에러 없이 게임 진행 유지.

- **그 외 스탯 값이 정의된 범위를 초과하는 경우** (예: `is_boss = false`인데 `base_hp > 65`, 또는 `is_boss = true`인데 `base_hp < 150` — **0 이하 `base_hp`는 제외, 위 항목 참조**): 데이터 오류로 간주. 로드 시 `push_warning("Enemy [id] stat out of expected range for is_boss=[value]")` 출력하되 게임은 해당 값 그대로 사용 (강제 클램핑 없음 — 디자이너가 의도적으로 범위 밖 값을 테스트할 수 있어야 함). 동료 데이터와 동일 원칙.

- **적 스킬이 `target_type="ally"`/`"all_allies"`(아군, 즉 다른 적을 대상)를 사용하는 경우 — 스키마상 가능하나 MVP 스코프 밖**: `SkillData`는 `#10 동료 데이터`와 공유되므로 EnemyData의 `skill_id`가 가리키는 스킬도 이론상 `target_type="ally"`를 가질 수 있다(적이 다른 적을 힐/버프하는 "지원형 적"). **MVP 4종(일반 3 + 보스 1)은 전원 `target_type="enemy"` 스킬만 사용한다** — 적 힐러/버퍼는 Full Vision 스코프. `#1 턴제 전투`가 적 파티 내 아군 타겟팅을 아직 지원하지 않는 한, 빌드 검증 도구는 EnemyData가 참조하는 SkillData의 `target_type`이 `"enemy"`가 아니면 경고를 출력한다.

- **던전 방에 배치할 적 데이터가 없는 경우** (예: `#2 랜덤 던전`이 빈 방 유형에 적을 요청): 이 시스템은 해당 상황을 감지하지 않는다 — 적어도 MVP 4종(일반 3 + 보스 1)이 항상 존재함을 전제로 하며, 방 배치 실패는 `#2 랜덤 던전`의 책임 범위.

## Visual/Audio Requirements

이 시스템은 시각 자산을 소유하지 않는다 — 스프라이트 렌더링은 `#1 턴제 전투`/`#20 UI/HUD`가, 오디오는 `#21 오디오`가 소유한다. 이 시스템의 책임은 아트 바이블이 요구하는 시각적 차별화를 `sprite_id`/`is_boss` 필드로 지원 가능하게 하는 것뿐이다.

**아트 바이블 준수 요구사항** (design/art/art-bible.md):
- 실루엣(섹션 3-1): 일반 적은 오목/비대칭 실루엣(소형: 삼각 돌출 2개+, 중형: 역삼각형 상반신/비대칭 팔) 필수. 보스는 동료 스프라이트 면적 4배 이상 + 내부 네거티브 스페이스 1개 이상 — `is_boss=true` 적의 `sprite_id` 에셋은 이 크기 기준을 충족해야 한다.
- 색상(섹션 4-2): 적 관련 시각 요소(rim light, 위험 표시)는 위협홍 계열(`H:0–15°`, 기준색 `#C0392B`)만 사용하며, 동료 warm 계열(`H:280°–130°`)과 최소 30° 차이를 유지한다.
- 배치(섹션 3-2): 보스 방은 십자형 레이아웃 예정(*GDD 확정 후 조정*) — 스폰 공간 요구사항 자체는 `#2 랜덤 던전` 소유.

오디오: 이 시스템은 오디오 필드를 갖지 않는다(SkillData/EnemyData에 sfx 참조 없음). 적 조우/피격 SFX는 `#21 오디오`가 `#1 턴제 전투` 이벤트에 훅을 걸어 재생한다.

📌 **Asset Spec** — Visual/Audio 요구사항이 정의됨. 아트 바이블 섹션 5-9 완성 후 `/asset-spec system:적-데이터`로 에셋별 스펙을 뽑을 수 있다.

## UI Requirements

이 시스템은 UI를 소유하지 않는다. 전투 중 적 이름·HP·상태 표시는 `#20 UI/HUD`가 담당하며, `EnemyData.name`과 초기 `base_hp`를 데이터 소스로 참조한다(실시간 HP는 `#13 런 상태 관리` 소유). 아트 바이블 섹션 3-3(사각형 단일 원칙, 최소 터치 44×44px)은 `#20 UI/HUD` GDD 작성 시 적용 대상.

## Acceptance Criteria

1. **GIVEN** 게임이 시작될 때, **WHEN** `EnemyRegistry`가 `assets/data/enemies/`의 파일들을 정렬된 순서로 로드하면, **THEN** MVP 4종(노멀 3종 + 보스 1종)이 모두 로드되어 `push_error`/`push_warning` 호출 횟수가 0이고, 4개 `EnemyData` 인스턴스 모두 non-null이며 각각 고유한 `id`를 가진다.

2. **GIVEN** 로드된 EnemyData 리소스 하나를 검사할 때, **WHEN** 필드를 확인하면, **THEN** `id`/`name`/`sprite_id`/`base_hp`/`base_atk`/`base_def`/`base_spd`/`skill_id`/`is_boss` 9개 필드가 모두 정의된 타입으로 non-null이며, 경로가 `assets/data/enemies/[id].tres` 규칙을 따른다.

3. **GIVEN** 로드된 EnemyData 리소스, **WHEN** `base_hp`/`base_atk`/`base_def`/`base_spd` 필드를 반복 조회하면, **THEN** 매번 동일한 값이 반환된다 (이 리소스는 불변 데이터이며, 조회 자체가 값을 바꾸지 않음을 검증한다 — 실시간 전투 상태 반영 여부는 `#13 런 상태 관리`의 AC 범위이며 이 시스템의 대상이 아니다).

4. **GIVEN** 로드된 EnemyData 리소스, **WHEN** 그 전투 스탯 필드를 조회하면, **THEN** 조회값이 디스크상의 `.tres` 파일에 저장된 값과 정확히 일치한다 (전투 시작 시점 값과의 일치 여부는 `#1 턴제 전투`의 AC 범위).

5. **GIVEN** `EnemyRegistry`에서 조회한 EnemyData, **WHEN** `id`/`is_boss`를 확인하면, **THEN** `is_boss=true`/`false` 값이 저장된 그대로 정확히 반환된다. (파티/방 배치 로직에서 실제로 이 값에 따라 스폰이 분기되는지는 `#2 랜덤 던전`의 AC 범위이며 여기서 보장하지 않는다.)

6. **GIVEN** 노멀 적 3종(속도형/밸런스형/탱커형) 데이터, **WHEN** 스탯을 확인하면, **THEN** `base_hp`/`base_atk`/`base_def`/`base_spd`가 각각 25–65 / 8–18 / 3–12 / 1–9 범위 내에 있다. (GDD 예시 배분표의 정확한 숫자는 참고용 placeholder이며 이 AC의 대상이 아니다 — 정확값 일치는 `production/qa/smoke-*.md`의 ADVISORY 스모크 체크로 별도 관리한다.)

7. **GIVEN** 보스 데이터, **WHEN** 스탯을 확인하면, **THEN** `base_hp`/`base_atk`/`base_def`/`base_spd`가 각각 150–300 / 15–25 / 8–20 / 4–9 범위 내에 있다 (`base_def` 하한 2026-08-02 재조정, Tuning Knobs 참조). (예시 배분 정확값은 6번과 동일하게 ADVISORY 스모크 체크로 분리.)

8. **GIVEN** 동일한 `id`를 가진 EnemyData 파일 2개, **WHEN** `EnemyRegistry`가 파일명 오름차순 정렬 후 로드하면, **THEN** 정렬 순서상 첫 번째 파일만 사용되고 `push_error`가 출력되며 게임이 중단되지 않는다. (테스트는 이름이 알려진 두 고정 fixture 파일로 정렬 결과를 검증한다.)

9. **GIVEN** 빌드 검증 도구가 실행될 때, **WHEN** 어떤 EnemyData의 `skill_id`가 존재하지 않는 SkillData를 참조하거나, 참조하는 SkillData의 `target_type`이 `"enemy"`가 아니거나, `damage_multiplier`가 1.4를 초과하면, **THEN** 빌드 단계에서 경고가 출력된다. (런타임 폴백은 Edge Cases의 별도 세이프티넷이며 이 AC의 대상이 아니다.)

10. **GIVEN** `sprite_id`가 비어있는 EnemyData, **WHEN** 스프라이트 로더가 fallback(`sprite_missing.png`)을 요청하면, **THEN** non-null `Texture2D`가 반환된다. (실제 화면 렌더링 확인은 Visual/UI 스토리 타입 — ADVISORY 등급, 스크린샷으로 별도 확인.)

11. **GIVEN** `base_hp ≤ 0`을 가진 EnemyData, **WHEN** `EnemyRegistry`가 이를 로드하려 하면, **THEN** `push_error`가 출력되고 해당 EnemyData는 로드되지 않는다 (게임에 등록되지 않음).

12. **GIVEN** `is_boss=false`인 적의 `base_hp`가 65를 초과하는 등 (0 이하 제외) 정의된 범위를 벗어날 때, **WHEN** 데이터를 로드하면, **THEN** `push_warning`이 기록되지만 값은 강제 clamp 없이 입력된 그대로 유지된다.

13. **GIVEN** 로드된 EnemyData, **WHEN** `base_atk`/`base_spd`/`skill_id` 필드를 조회하면, **THEN** 세 값 모두 non-null로 반환된다. (이 값들을 사용한 AI 행동 결정의 정오는 `#7 적 AI`의 AC 범위이며 이 시스템의 대상이 아니다.)
