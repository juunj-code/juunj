# 씬 관리 (Scene Management)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: Foundation 인프라 — 직접 필라를 구현하지 않고 모든 필라를 가능하게 하는 기반
> **Creative Director Review**: Skipped — Lean 모드

## Overview

씬 관리 시스템은 바람의 탑의 모든 게임 화면(메인메뉴 · 파티 선택 · 던전 탐색 · 전투 · 런 결과) 사이의 전환을 중앙에서 제어하는 Foundation 레이어 인프라다. Godot 4.6 `SceneManager` Autoload 싱글톤으로 구현되며, 씬 전환 요청을 받아 적절한 전환 연출(즉시·페이드·플래시)을 실행하고, 웹 내보내기 초기 로딩 시간을 최소화하기 위한 씬 프리로드 전략을 담당한다.

이 시스템 자체는 "게임 내 상태"를 모른다 — 어떤 씬으로 전환할지는 소비 시스템(#13 런 상태 관리, #2 랜덤 던전 등)이 결정하며, 씬 관리는 그 요청을 안전하고 일관된 방식으로 실행하는 전용 인프라 계층이다. 광고 통합(#18)·오디오(#21)·설정(#23)의 씬 생명주기 훅 연결점도 이 시스템이 제공한다.

## Player Fantasy

플레이어는 "씬 관리 시스템"을 의식하지 않는다 — 이 시스템이 완벽히 보이지 않을 때 성공이다.

플레이어가 실제로 느끼는 것:
- **매끄러운 흐름**: 던전에서 전투로, 전투에서 다시 던전으로의 전환이 눈에 띄는 끊김 없이 자연스럽다. 화면 전환이 너무 빠르지도(시선이 못 따라감), 너무 느리지도(대기감이 쌓임) 않다.
- **동료 발견 순간의 연출 강화**: 이 시스템의 FlashTransition은 그 연출을 위한 **확장점(hook)**을 제공한다 — 현재 FlashOverlay는 `#FFFFFF` 고정 컬러의 범용 플래시일 뿐이며, 동료별 `color_accent`(#10 동료 데이터)를 실제로 반영하는 것은 `#3 동료 해금`의 책임이다 (Open Questions #1 참조). "색감이 살아나는 연출" 자체는 이 시스템이 아직 만들어내지 않는다.
- **브라우저에서 즉각 시작**: 첫 로딩 이후 런을 시작하는 데 눈에 띄는 대기 시간이 없어야 한다. 두 번째 런부터는 "이미 준비된" 느낌이어야 한다.

이 시스템이 실패하면 플레이어가 느끼는 것: 검은 화면이 길게 유지되거나, 전환 도중 프레임이 끊기거나, 브라우저에서 "응답 없음"이 뜬다 — 세션을 즉시 종료시키는 신뢰 붕괴 순간이다.

## Detailed Rules

### Scene Catalog

| ID | 씬 이름 | Godot 파일 | 역할 |
|----|---------|-----------|------|
| S-01 | Boot | `Boot.tscn` | 웹 초기 로딩 + 핵심 씬 프리로드 → 자동으로 MainMenu 전환 |
| S-02 | MainMenu | `MainMenu.tscn` | 타이틀 화면, 최고 기록 표시, 런 시작 진입점 |
| S-03 | PartySelect | `PartySelectScreen.tscn` | 런 시작 전 파티 구성 선택 |
| S-04 | DungeonExploration | `DungeonScreen.tscn` | 던전 탐색 뷰 (방 이동, 히든 방 탐색) |
| S-05 | BattleScreen | `BattleScreen.tscn` | 턴제 전투 인터페이스 |
| S-06 | RunResult | `RunResultScreen.tscn` | 런 결과 + 동료 영구 해금 표시 |

### Transition Graph

```
Boot ──(자동)──→ MainMenu
MainMenu ──(런 시작)──→ PartySelect
PartySelect ──(확인)──→ DungeonExploration
DungeonExploration ──(전투 진입)──→ BattleScreen
BattleScreen ──(전투 종료)──→ DungeonExploration
DungeonExploration ──(런 종료/전멸)──→ RunResult
RunResult ──(다음 런)──→ PartySelect
RunResult ──(메인메뉴)──→ MainMenu
[모든 씬] ──(설정)──→ Settings CanvasLayer (씬 교체 아님, 오버레이)
```

### Transition Types

| 타입 | 연출 | 지속시간 | 사용 상황 |
|------|------|----------|-----------|
| `INSTANT` | 전환 없음 | 0ms | Boot → MainMenu (로딩 직후 즉시) |
| `FADE` | 검은 화면 인→전환→아웃 | 300ms + 300ms | 대부분의 일반 전환 |
| `FLASH` | 흰 화면 플래시→전환→아웃 | 150ms + 150ms | 히든 동료 발견 직후 전환 전용 |

### Core Rules

1. **모든 씬 전환은 SceneManager를 통해서만**: `get_tree().change_scene_to_file()` 직접 호출 금지 — 이 규칙은 SceneManager를 호출하는 **소비 시스템**에 적용된다. SceneManager 자신의 내부 구현은 `ResourceLoader.load_threaded_get()` → `get_tree().change_scene_to_packed()`(PackedScene 기반)를 사용한다 — `change_scene_to_file()`(동기/블로킹)을 내부적으로도 사용하면 백그라운드 로딩 자체가 무력화되므로 명시적으로 구분한다.
2. **전환 중 중복 요청 차단**: "전환 진행 중"은 `Idle`이 아닌 모든 상태(`Transitioning`, `Loading`, `Displaying`)를 뜻한다 — 가드는 **Displaying의 아웃 트윈(FADE_OUT_MS/FLASH_OUT_MS)이 완료되어 Idle로 복귀하는 시점에만** 해제된다(씬이 인스턴스화된 시점이 아님). 이 창 안의 추가 요청은 드롭, `push_warning` 기록. 전환 완료 후 소비 시스템이 재요청해야 한다.
3. **설정은 씬 전환 대상이 아님**: 설정 화면은 CanvasLayer 오버레이로 현재 씬 위에 표시. 씬 트리를 교체하지 않는다.
4. **Boot씬은 프리로드 전용**: Boot는 핵심 씬 패키지를 백그라운드 로딩 후 자동 전환한다. 플레이어가 Boot를 의식하는 경험은 "첫 로딩 진행바" 딱 한 번. **`BOOT_PRELOAD_TIMEOUT_MS`**(Formula ③ 참조) 초과 시 완료된 씬만 가지고 MainMenu로 진행하고, 미완료 씬은 실제 첫 내비게이션 시점에 지연 로드(lazy-load)한다 — Boot가 무한정 멈추지 않는다.
5. **씬 생명주기 신호 제공**: `scene_loading_started`, `scene_ready`, `scene_exited` 신호를 발신한다. #18·#21·#23은 이 신호를 구독해 씬별 동작을 연결한다.

### States and Transitions

| 상태 | 트리거 | 다음 상태 |
|------|--------|-----------|
| Idle | 초기 상태 | Transitioning (go_to() 호출 시) |
| Transitioning | go_to() 호출 | Loading (씬 미리 로드 안 된 경우) / Displaying (프리로드된 씬) |
| Loading | ResourceLoader 백그라운드 로드 | Displaying (완료 시) / Idle (타임아웃 시, 이전 씬 유지) |
| Displaying | 씬 준비 완료 + 전환 연출 아웃 완료 | Idle |

**"전환 진행 중" 정의 (Core Rule 2 참조)**: `{Transitioning, Loading, Displaying}` 전체 — `go_to()`를 안전하게 받아들이는 상태는 `Idle` 하나뿐이다.

**탭 백그라운드와 상태 상호작용**: 탭 백그라운드 중 스킵 규칙(Edge Cases 참조)은 `Transitioning`/`Displaying`(순수 연출 애니메이션)에만 적용된다. `Loading` 상태의 `t_load_elapsed`는 실제 wall-clock이 아니라 **`_process(delta)` 누적치**로 측정한다 — 브라우저가 백그라운드 탭에서 `_process` 호출 자체를 멈추므로(엔진이 아니라 브라우저의 requestAnimationFrame 정지가 원인) 이 방식이면 백그라운드 동안 `t_load_elapsed`가 자연히 멈춘다. 즉 로드가 90% 진행된 상태로 탭이 백그라운드로 가도, 그 시간만큼 타임아웃 판정이 부당하게 앞당겨지지 않는다.

## Formulas

씬 관리는 게임플레이 수치 공식을 갖지 않는 순수 인프라 시스템이다. 대신 플레이어 경험을 정량적으로 보장하는 타이밍 예산과 성능 임계값을 여기서 확정한다.

**① 전환 연출 타이밍**

| 심볼 | 타입 | 값 | 설명 |
|------|------|----|------|
| `FADE_IN_MS` | int (상수) | 300 | 페이드 인(현재 씬 암전) 지속 시간 (ms) |
| `FADE_OUT_MS` | int (상수) | 300 | 페이드 아웃(새 씬 점등) 지속 시간 (ms) |
| `FLASH_IN_MS` | int (상수) | 150 | 플래시 인(백색 화면) 지속 시간 (ms) |
| `FLASH_OUT_MS` | int (상수) | 150 | 플래시 아웃(새 씬 점등) 지속 시간 (ms) |

총 FADE 체감 시간 = `FADE_IN_MS + 씬 로드 시간 + FADE_OUT_MS`

**즉시 소요시간 상한 (2026-07-26 리비전 — 리뷰에서 지적된 자기모순 해결)**: 씬 로드 시간의 최댓값은 `SCENE_LOAD_TIMEOUT_MS`(10000ms)이므로, 실패 케이스의 이론적 최장 체감 시간은 `FADE_IN_MS(300) + SCENE_LOAD_TIMEOUT_MS(10000) = 10300ms`의 암전이다. 이는 이 문서 자신이 Player Fantasy에서 신뢰 붕괴 조건으로 지목한 "검은 화면이 길게 유지"와 정면으로 충돌한다. 완화책: `t_load_elapsed`가 **2500ms**를 넘으면(하드 실패 이전, 소프트 신호) FadeOverlay 위에 은은한 "로딩 중..." 인디케이터를 표시한다 — 완전한 무반응 암전과 "느리지만 진행 중"을 구분한다. 타임아웃 확정 시(Edge Cases 참조) FadeOverlay는 `FADE_OUT_MS`에 걸쳐 원래 씬으로 복귀한 뒤 그 위에 "다시 시도" UI를 표시한다 — 실패 후에도 화면이 검게 남지 않는다.

**런 단위 누적 예산**: 위 값은 단일 전환 기준이다. MVP 세션 길이(10~20분, 전투 8~12회 가정) 기준 FADE 전환만으로 누적 4.8~7.2초의 암전이 발생한다 — 이는 하드 캡이 아니라 **관찰 지표**로, `/prototype` 단계에서 실측 세션 길이 대비 비율을 확인하고 필요 시 전투 진입/복귀 전환을 반복 노출 시 더 짧은 변형(예: FADE_IN_MS를 150ms로 단축)으로 낮추는 것을 고려한다.

**② 씬 로드 타임아웃**

| 심볼 | 타입 | 값 | 설명 |
|------|------|----|------|
| `t_load_elapsed` | int (ms, `_process(delta)` 누적치 — wall-clock 아님) | 0 이상 | 로드 요청부터 PackedScene 준비까지 경과 시간. delta 누적이므로 브라우저 탭 백그라운드 중(엔진 `_process` 자체가 호출되지 않는 구간) 자동으로 정지한다 |
| `SCENE_LOAD_TIMEOUT_MS` | int (상수) | 10000 | 씬 로드 대기 최대 시간 (ms) |
| `LOADING_INDICATOR_THRESHOLD_MS` | int (상수) | 2500 | 이 값 초과 시 "로딩 중..." 소프트 인디케이터 표시 (하드 실패 아님) |

`t_load_elapsed > SCENE_LOAD_TIMEOUT_MS` 시 로드 실패 확정, 무한 대기 없음. 웹 환경의 네트워크 지연 흡수를 위해 데스크톱 기준보다 넉넉하게 설정.

**웹 익스포트 스레드 로딩 리스크 (2026-07-26 리비전 — 리뷰에서 발견된 미플래그 리스크)**: "백그라운드 로딩"은 `ResourceLoader.load_threaded_request()`를 전제하나, Godot 웹 익스포트의 진짜 OS 스레드 활용은 "Threads" 빌드 변형에서만 가능하며 이는 호스팅 서버가 `SharedArrayBuffer`를 위한 COOP/COEP 크로스오리진 격리 헤더를 제공해야 동작한다. 이 헤더가 없으면 Threads 빌드는 로드 자체가 실패하거나, "Regular"(비-스레드) 변형에서는 스레드 로딩 API가 메인 스레드 프레임 예산을 FADE 트윈과 경쟁하며 잠식한다(진짜 병렬 작업이 아님). 배포 예정 플랫폼(itch.io)은 프로젝트별로 COOP/COEP를 명시적으로 켜야만 이 헤더를 제공한다 — Open Questions #4 참조, 구현 전 ADR 필수.

**③ Boot 프리로드 씬 목록 (고정)**

| 씬 | 프리로드 이유 |
|----|-------------|
| `MainMenu.tscn` | Boot 완료 즉시 표시 |
| `PartySelectScreen.tscn` | 첫 런 진입 속도 |
| `BattleScreen.tscn` | 런 중 가장 빈번히 전환되는 씬 |

`DungeonScreen.tscn` 제외 — 던전은 런타임 절차적 생성이 병목이므로 씬 파일 프리로드 효과가 낮음.

**`BOOT_PRELOAD_TIMEOUT_MS`**: 8000 (상수, 3개 씬 합산 기준). 초과 시 Core Rule 4에 따라 완료된 씬만으로 MainMenu 진행 — Boot가 무한정 대기하지 않는다 (Tuning Knobs 참조).

## Edge Cases

- **전환 중 추가 전환 요청**: 드롭하고 `push_warning`을 남긴다. 진행 중인 전환이 완료된 후 소비 시스템이 재요청해야 한다.

- **씬 로드가 `LOADING_INDICATOR_THRESHOLD_MS`(2500ms) 초과**: 하드 실패 아님 — FadeOverlay 위에 "로딩 중..." 소프트 인디케이터를 표시해 무반응 암전과 구분한다.

- **씬 로드가 `SCENE_LOAD_TIMEOUT_MS`(10초) 초과**: 로드 실패로 처리 — FadeOverlay가 `FADE_OUT_MS`에 걸쳐 원래(유지된) 씬으로 복귀하고 Idle로 전이하며 `push_error` 기록. `#20 UI/HUD`를 통해 "다시 시도" 안내를 (검은 화면이 아닌) 복귀된 이전 씬 위에 표시. 웹 환경의 네트워크 단절이 가장 흔한 원인.

- **Boot 프리로드가 `BOOT_PRELOAD_TIMEOUT_MS`(8초) 초과**: 완료된 씬만으로 MainMenu 진행. 미완료 씬은 실제 첫 내비게이션 시점에 지연 로드하며, 그 경우 해당 전환은 일반 `SCENE_LOAD_TIMEOUT_MS` 경로를 탄다(프리로드 실패가 곧 게임 진행 불가를 의미하지 않는다).

- **Boot씬 프리로드 실패(파일 경로 오류 등)**: 개발 빌드 한정 프로그래밍 오류. `assert(false, "Boot preload failed: ...")` 로 즉각 크래시 — 릴리스 빌드는 export 템플릿이 파일 포함을 보장하므로 이 경로는 존재하지 않는다.

- **설정 오버레이가 열린 상태에서 씬 전환 요청**: 오버레이를 먼저 닫고 전환을 실행한다. CanvasLayer이므로 씬 교체 시 자동 제거되지만, 닫기 애니메이션이 있다면 완료 후 전환.

- **브라우저 탭이 백그라운드로 전환된 상태의 전환 중**: 이 규칙은 `Transitioning`/`Displaying`(순수 연출 애니메이션) 상태에만 적용된다 — Godot 자체가 `process_mode`로 Tween을 멈추는 게 아니라, **브라우저가 백그라운드 탭에서 requestAnimationFrame 호출을 정지**시켜 엔진의 메인 루프 전체가 멈춘다. 탭 재활성화 시 다음 프레임의 delta가 매우 크게 들어와 진행 중이던 Tween이 사실상 즉시 완료값(1.0)으로 도달한다 — 별도의 "스킵 로직"이 아니라 이 delta 처리 방식의 결과다. `Loading` 상태 중이었다면 `t_load_elapsed`가 delta 누적(위 Formula ②)이라 백그라운드 동안 자연히 멈추므로, 탭 이탈 시간만큼 부당하게 타임아웃되지 않는다.

- **Transition Graph에 없는 씬 전환 요청** (예: BattleScreen → MainMenu 직접): 허용하되 `push_warning` 기록. 씬 관리는 흐름 검증자가 아니라 전환 실행자다 — 흐름 제어는 #13 런 상태 관리 책임. (`#13`의 GDD/AC가 "RunResult는 항상 거쳐간다"는 보장을 소유해야 한다 — 이 시스템은 그 보장을 하지 않는다.)

## Visual/Audio Requirements

이 시스템은 전환 연출을 위한 최소한의 시각 자산을 직접 소유한다:
- **FadeOverlay**: 전체 화면을 덮는 검은 CanvasLayer. FADE 전환 시 alpha 0→1→0 트윈.
- **FlashOverlay**: 전체 화면을 덮는 흰 CanvasLayer. FLASH 전환 시 alpha 0→1→0 트윈.

FadeOverlay 컬러: `#000000` 고정. FlashOverlay 컬러: 현재 `#FFFFFF` 임시값 — art bible 완성 후 "바람빛" 컬러 계열로 재검토.

오디오: 이 시스템은 오디오를 직접 재생하지 않는다. `#21 오디오`가 `scene_ready` / `scene_exited` 신호를 구독해 BGM 크로스페이드를 처리한다.

📌 **Art Flag**: FlashOverlay 컬러를 `/art-bible` 완성 후 업데이트할 것.

## Acceptance Criteria

1. (Core Rule 1 – 중앙화) GIVEN 전투가 종료된 상태에서 WHEN `#13`이 `SceneManager.go_to(S-04, FADE)`를 호출하면 THEN `get_tree().change_scene_to_file()` 직접 호출 없이 DungeonScreen으로 전환되고 `scene_ready` 신호가 발신된다.

2. (Core Rule 2 – 중복 차단) GIVEN 씬 전환이 진행 중인 상태에서 WHEN 두 번째 `go_to()` 호출이 발생하면 THEN 두 번째 요청은 드롭되고 `push_warning`이 기록되며 진행 중 전환은 영향받지 않는다.

3. (Core Rule 3 – 설정 오버레이) GIVEN 설정 오버레이가 열린 상태에서 WHEN 씬 전환 요청이 발생하면 THEN 오버레이가 먼저 닫히고 이후 씬 전환이 실행된다.

4. (Formula ① – FADE 타이밍, **BLOCKING** — Tween 설정값 검증) GIVEN 전환 타입이 FADE인 상태에서 WHEN 전환 Tween이 구성되면 THEN FadeOverlay 암전 Tween의 duration이 `FADE_IN_MS`(300)이고 복원 Tween의 duration이 `FADE_OUT_MS`(300)이다 (코드 상 Tween 설정값 검사 — 실시간 대기로 측정하지 않는다). 실제 체감 부드러움 확인은 별도 **ADVISORY** 스크린샷/수동 확인(`.claude/docs/coding-standards.md`의 Visual/Feel 등급)이며 이 AC의 대상이 아니다.

5. (Formula ① – FLASH 타이밍, **BLOCKING** — 4번과 동일한 검증 방식) GIVEN 전환 타입이 FLASH인 상태에서 WHEN 전환 Tween이 구성되면 THEN FlashOverlay 피크 Tween duration이 `FLASH_IN_MS`(150)이고 복원 Tween duration이 `FLASH_OUT_MS`(150)이다. 체감 확인은 4번과 동일하게 ADVISORY로 분리.

6. (Formula ② – 로드 타임아웃) GIVEN 씬 로드가 시작된 상태에서 WHEN `t_load_elapsed`(주입 가능한 clock/timer 기반 — 실제 10초 대기 없이 모의 시간 진행으로 테스트) 가 10000ms에 도달해도 씬이 준비되지 않으면 THEN Idle로 복귀하고 이전 씬을 유지하며 `push_error`가 기록되고, FadeOverlay는 `FADE_OUT_MS`에 걸쳐 복귀된 이전 씬을 드러낸다.

7. (Formula ③ – Boot 프리로드, **테스트 범위 조정**) GIVEN 게임이 브라우저에서 처음 실행된 상태에서 WHEN Boot씬이 완료되면 THEN `MainMenu.tscn`, `PartySelectScreen.tscn`, `BattleScreen.tscn` 3개 씬이 캐시(딕셔너리, scene_id 키)에 존재하고, 이후 `go_to()`가 이 캐시를 우선 조회한다 (원본의 "추가 파일 I/O가 발생하지 않는다"는 계측 없이는 관찰 불가능한 주장이므로, 대신 캐시 히트를 테스트 가능한 대리 지표로 사용한다).

8. (신호 – 오디오 연결) GIVEN `#21 오디오`가 `scene_ready` 신호를 구독한 상태에서 WHEN DungeonScreen 전환이 완료되면 THEN `scene_ready` 신호가 발신되어 오디오 시스템이 던전 BGM을 재생할 수 있다.

9. (전환 그래프) GIVEN `SceneManager.go_to(S-03, FADE)`가 호출되면(호출자가 #13이든 UI 버튼 핸들러든, 이 시스템은 호출자를 모른다) THEN PartySelectScreen으로 FADE 전환된다. (RunResult 화면의 "다음 런" 버튼이 실제로 이 호출을 트리거하는지는 `#13`/`#20`의 AC 범위이며 이 시스템의 대상이 아니다.)

10. (Edge Case – 탭 백그라운드) GIVEN FADE 전환 중 브라우저 탭이 백그라운드로 전환된 상태에서 WHEN 탭이 재활성화되면 THEN 전환 연출을 즉시 완료 상태로 스킵하고 Idle로 복귀하며 새 씬이 정상 표시된다.

11. (Edge Case – 미등록 전환 그래프 경로) GIVEN `Transition Graph`에 명시되지 않은 씬 쌍으로 `go_to()`가 호출되면(예: BattleScreen → MainMenu) THEN 전환은 정상 실행되고 `push_warning`이 기록되며, 실행 자체는 차단되지 않는다.
