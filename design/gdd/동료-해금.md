> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 발견의 기쁨 / 성장은 영원하다
> **Creative Director Review**: Skipped — Lean 모드

## Overview

동료 해금 시스템은 히든방에서 동료를 발견하는 순간의 흐름을 오케스트레이션하는 Feature 레이어 시스템이다. #9 히든 트리거로부터 `companion_discovered(companion_id)` 신호를 수신해, 이번 런 발견 목록(`RunManager.discovered_companions`)에 추가하고 발견 연출 UI를 표시한다. 런 종료 후 #14 영구 진행이 실제 영속 해금을 처리하므로, 이 시스템은 "발견 순간"만 담당한다 — 영속화는 #14 소유.

## Player Fantasy

"○○가 동료가 되었다!" — 카드가 나타나는 순간. 런이 실패해도 이 순간의 발견은 남는다는 확신.

## Detailed Rules

### 발견 흐름

```
#9 → companion_discovered(companion_id) 수신
  ↓
if RunManager.state != "EXPLORING": push_error(...); return  # 2026-07-26 추가 — 업스트림 보장에만 의존하지 않는 방어선
  ↓
이미 discovered_companions에 있으면 즉시 리턴 (중복 방지)
  ↓
#10 CompanionData 조회 (2026-07-26 리비전 — 목록 추가보다 먼저 실행, fail-fast)
  실패 시: push_warning + 흐름 중단 (Edge Cases 참조, discovered_companions에 추가 안 함)
  성공 시: 동료 이름·사연·초상화·컬러 로드
  ↓
RunManager.discovered_companions에 companion_id 추가  # 조회 성공이 확인된 후에만 추가
  ↓
await SceneManager.go_to(current_scene, FLASH, companion.color_accent)  # 2026-07-26 추가 — 색감 연출 실제 트리거
  ↓
companion_unlocked_this_run(id, name, description, portrait_path, color_accent) 신호 발신
  → #20 UI/HUD가 발견 팝업 표시 (블로킹)
  ↓
await popup_confirmed  # 2026-07-26 추가 — 플레이어 탭 시그널에 대한 명시적 대기 (무기한, 타임아웃 없음)
  ↓
팝업 닫기 → 던전 탐색 재개
```

**런 종료 처리 (2026-07-26 리비전 — #14의 최신 인터페이스에 맞춤)**: 런 종료 시 `#13 런 상태 관리`가 `RunManager.discovered_companions`와 `current_floor`를 `#14.commit_run_end(discovered_ids, floor)`에 전달한다 (구 버전이 언급한 `unlock_companion()` 개별 호출은 `#14` 리비전에서 배치 처리로 대체됨). 이 시스템은 런 종료 처리에 전혀 관여하지 않는다 — 검증은 `#13`/`#14`의 AC 범위(Acceptance Criteria 참조).

**배치 밖 단독 호출 경로**: `#14`는 `unlock_companion(id)`를 디버그/단독 호출용으로도 노출한다. 이 시스템은 그 경로를 직접 사용하지 않지만, `#14`가 발신하는 `companion_unlocked` 신호(런 종료 배치와 별개)를 구독해 팝업 없이 도감 갱신 등 부가 처리가 필요한지는 `#16 런 결과`/`#20`이 결정 — 이 GDD의 범위 밖.

### 핵심 API

| 신호/메서드 | 타입 | 설명 |
|-------------|------|------|
| `companion_discovered(id)` | 신호 수신 | #9로부터 수신, 발견 흐름 시작 |
| `companion_unlocked_this_run(id: String, name: String, description: String, portrait_path: String, color_accent: Color)` | 신호 발신 (2026-07-26 리비전 — 타입 명시 + `description`/`color_accent` 추가) | UI 팝업 표시 트리거. `description`·`color_accent`는 `#10 동료 데이터`가 정의한 발견 연출 인터페이스 계약(4개 필드) 중 이 시스템이 누락했던 두 필드 |

### Core Rules

1. **런 내 중복 발견 방지**: `RunManager.discovered_companions`에 이미 있으면 전체 흐름 스킵. 신호 중복 도달에도 안전.
2. **전투 중 발동 없음, 방어선 추가 (2026-07-26 리비전)**: 히든방 진입은 탐색 상태에서만 발생하도록 `#2`/`#9`가 보장하지만, 이 시스템도 `RunManager.state != "EXPLORING"`일 때 `push_error` 후 즉시 반환하는 저비용 방어선을 둔다 — 이 시스템이 흐름의 최종 종착점이라 업스트림 보장에만 전적으로 의존하는 것은 위험하다(잘못된 시그널 연결·디버그 훅 등).
3. **팝업은 블로킹, 구현 패턴 명시 (2026-07-26 리비전)**: 팝업이 표시된 동안 던전 이동 입력 비활성 (#20 UI/HUD 책임). 이 시스템의 발견 흐름은 `await popup_confirmed` 형태로 플레이어 탭 시그널을 기다린다 — 수동 토글 bool이 아니라 시그널 `await`로 구현해야 예외/조기 반환 경로에서 입력 잠금이 풀리지 않는 버그를 피한다.
4. **런 내 발견 데이터는 RunManager 소유**: 이 시스템은 `RunManager.discovered_companions`에 추가만 하고 직접 보관하지 않는다.

## Edge Cases

- **#10에 companion_id가 없음**: `CompanionData` 조회 실패 → `push_warning("Unknown companion_id in unlock flow: [id]")` + 발견 흐름 중단 (팝업 없음, discovered_companions에도 추가 안 함). 유효하지 않은 동료를 발견한 것으로 처리하지 않는다.

- **팝업 표시 중 앱 백그라운드 전환**: Godot 웹 탭 비활성 시 입력 대기 유지. 재활성화 시 팝업 그대로 표시.

- **런 종료 직전 동료 발견**: 발견 팝업 → 확인 탭 → 던전 재개 흐름 완료 후 런 종료. 팝업 표시 도중 런이 종료되는 경우는 없음 — 전투방에서만 패배 가능하고 히든방에는 전투 없음.

## UI Requirements

이 시스템은 UI를 소유하지 않는다. 팝업은 `#20 UI/HUD` 소유하되, 아래 내용은 이 시스템이 신호로 전달하는 데이터를 반드시 반영해야 한다(2026-07-26 리비전 — `description`/`color_accent`/영속성 안내 추가):
- 동료 초상화 (CompanionData.portrait_id)
- 동료 이름 (CompanionData.name)
- 동료 사연 1~2줄 (CompanionData.description) — 이전 버전에서 누락됐던 필드
- 컬러 포인트 (CompanionData.color_accent) — FLASH 전환 및 팝업 테두리/강조색으로 활용
- "동료가 되었다!" 텍스트
- **영속성 안내** (2026-07-26 추가): "도감에 영구 등록됨" 등 이번 발견이 런 실패와 무관하게 남는다는 확신을 주는 짧은 문구 — Player Fantasy의 "런이 실패해도 이 순간의 발견은 남는다는 확신"이 실제 화면에 드러나야 함
- 확인 버튼 (탭)

## Acceptance Criteria

1. (발견 목록 추가) GIVEN `companion_discovered("hidden_archer_03")` 수신 WHEN `#10` 조회가 성공한 뒤 처리되면 THEN `RunManager.discovered_companions`에 `"hidden_archer_03"`이 추가된다. (조회가 목록 추가보다 먼저 실행됨 — 발견 흐름 참조.)

2. (팝업 트리거, 2026-07-26 리비전 — #20 렌더링 주장 제거) GIVEN `companion_discovered` 수신 WHEN #10에서 데이터 조회 성공 THEN `companion_unlocked_this_run(id, name, description, portrait_path, color_accent)` 신호가 올바른 인자로 발신된다. (실제 UI 팝업 렌더링은 `#20 UI/HUD`의 AC 범위 — 이 시스템은 신호 발신까지만 보증한다.)

3. (중복 방지) GIVEN `discovered_companions = ["hidden_archer_03"]`인 상태 WHEN `companion_discovered("hidden_archer_03")`가 다시 수신되면 THEN `discovered_companions`에 중복 추가되지 않고 `companion_unlocked_this_run` 신호가 재발신되지 않는다.

4. (유효하지 않은 ID) GIVEN 존재하지 않는 companion_id 수신 WHEN 처리되면 THEN `push_warning`이 기록되고 `discovered_companions`에 추가되지 않으며 신호가 발신되지 않는다.

5. (전투 중 오발동 방어, 2026-07-26 추가) GIVEN `RunManager.state != "EXPLORING"`인 상태에서 WHEN `companion_discovered(id)`가 수신되면 THEN `push_error`가 기록되고 흐름이 즉시 중단되며 `discovered_companions`는 변하지 않는다.

(구 AC5 "런 종료 후 영속"은 삭제됨 — 2026-07-26 리비전. 이 문서 자신이 "런 종료 처리에 관여하지 않는다"고 명시하므로 애초에 이 시스템의 AC 범위가 아니었다. 해당 검증은 `#13 런 상태 관리`의 AC8, `#14 영구 진행`의 AC9/9b가 이미 올바르게 담당한다.)

(구 AC6 "팝업 블로킹"도 삭제됨 — 2026-07-26 리비전. Core Rule 2에 따라 이 시스템은 상태 체크 외의 UI 입력 차단 로직을 전혀 소유하지 않으므로, `#20 UI/HUD` 쪽 검증에서 실제 이 시스템이 증명할 수 있는 부분이 없었다. 해당 AC는 `#20 UI/HUD` GDD의 AC 범위로 이관.)
