# 로컬 세이브 (Local Save)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 성장은 영원하다
> **Creative Director Review (CD-GDD-ALIGN)**: Skipped — Lean 모드

## Overview

로컬 세이브 시스템은 바람의 탑의 모든 영속 데이터(동료 해금 상태, 최고 층수 기록, 설정값 등)를 브라우저 로컬 저장소에 안전하게 기록·복원하는 Foundation 레이어 인프라다. 이 시스템 자체는 "무엇을 저장할지" 모른다 — 저장할 데이터의 스키마는 각 소비 시스템(#14 영구 진행, #23 설정)이 소유하며, 로컬 세이브는 이름 붙은 섹션(section key) 단위로 저장/불러오기·무결성 보장·버전 관리만 담당하는 범용 인프라 계층이다. #5 클라우드 세이브(Full Vision)는 이 시스템이 기록한 로컬 데이터를 읽어 동기화하는 상위 계층으로 존재한다. MVP에서는 클라우드 동기화 없이 이 시스템 하나로 "런이 끝나도 진행 상황이 남는다"는 필라 2를 기술적으로 뒷받침한다.

## Player Fantasy

플레이어는 "로컬 세이브 시스템"을 의식하지 않는다 — 오히려 이 시스템이 완벽히 보이지 않을 때 성공이다. 플레이어가 실제로 느끼는 것은 필라 2 "성장은 영원하다"의 약속: 런을 실패해도, 브라우저를 닫았다 다시 열어도 "그래도 ○○ 해금했다"는 확신.

이 시스템이 만드는 감각:
- **안심**: 창을 닫아도 지금까지 발견한 동료는 그대로 있다는 무의식적 신뢰. 이 신뢰가 깨지는 순간(세이브 유실) 게임 전체에 대한 신뢰가 무너진다 — 이 시스템의 실패는 다른 어떤 버그보다 치명적이다.
- **존재하지 않는 로딩 마찰**: "불러오기" 버튼을 누르는 행위 자체가 없다. 게임을 열면 이미 내 로스터가 거기 있다.

플레이어는 세이브 파일 구조를 경험하지 않는다. 실패한 런 뒤에도 "그래도 ○○ 해금했다"로 마무리되는 순간, 그 뒤에서 조용히 작동한 것이 이 시스템이다.

## Detailed Rules

### Core Rules

0. **오토로드**: 이 시스템은 Godot 전역 오토로드 싱글톤 `SaveManager`로 구현한다 (Foundation 레이어·무의존성·부팅 전 전역 접근 필요 — `#10 동료 데이터`의 `CompanionRegistry`/`#11 적 데이터`의 `EnemyRegistry`와 동일한 이유).

1. **범용 저장 API**: 다른 시스템은 이름 붙은 섹션 키(section key, 예: `"companion_unlocks"`, `"settings"`)로 자신의 데이터를 저장/조회한다. 로컬 세이브는 각 섹션의 내용(스키마)을 모른다 — 직렬화 가능한 데이터(Dictionary/Array 등)를 그대로 받아 저장하고, 조회 시 그대로 반환한다.
2. **저장 트리거는 명시적 호출뿐**: 자동 주기 저장(auto-save)은 MVP 범위 밖. 소비 시스템이 자신의 상태가 바뀔 때(동료 해금 순간, 설정 변경 순간) 명시적으로 저장을 요청한다.
3. **단일 파일, 다중 섹션**: 모든 섹션은 하나의 로컬 세이브 파일에 통합 저장한다(섹션별 개별 파일 아님) — 브라우저 저장소 쓰기 횟수를 최소화하고 원자적 갱신을 단순화하기 위함.
4. **원자적 쓰기(atomic write)**: 저장 시 임시 파일에 먼저 기록 → 쓰기 성공 확인 후 기존 세이브 파일과 교체. 쓰기 도중 중단(브라우저 강제 종료 등)되어도 기존 세이브 파일은 훼손되지 않는다.
5. **스키마 버전 관리**: 세이브 파일 최상위에 `schema_version`(int) 필드를 포함한다. 로드 시 현재 시스템이 기대하는 버전과 비교 — 낮으면 마이그레이션 필요 신호, 높으면(미래 버전 파일) 로드 거부.
6. **저장 완료 확인**: 저장 요청은 성공/실패를 명확히 반환(또는 시그널)한다 — 소비 시스템이 "저장됐다"고 UI에 표시하기 전에 이 확인을 기다려야 한다. **기술적 미검증 리스크 (2026-07-26 리비전 — 리뷰에서 확인된 구체 위험)**: Godot 웹(HTML5) export에서 `user://`는 IndexedDB 기반 가상 FS에 매핑되며, "임시 파일 쓰기 → 교체" 자체는 이 가상 FS 내에서 완료될 뿐 실제 IndexedDB 반영(durability)은 별도의 비동기 동기화 단계일 수 있다 — 즉 "쓰기 완료 확인" 신호가 **더 늦게 오는 게 아니라, 애초에 실제 디스크 반영 여부를 보지 못하는 신호일 위험**이 있다. `FileAccess.store_*`(Godot 4.4+에서 `bool` 반환으로 변경됨)는 가상 FS 내 쓰기 성공만 확인하며 IndexedDB 영속화 여부는 확인하지 않는다. 정확한 4.6 동작은 아키텍처 단계에서 검증 필요(→ ADR, Open Questions #2 참조 — 검증해야 할 구체 항목 명시됨).

### States and Transitions

| 상태 | 트리거 | 다음 상태 |
|------|--------|-----------|
| Idle | 초기 상태 | Loading(부팅 시 자동) 또는 Saving(요청 시) |
| Loading | 게임 부팅 시 자동 시작 | Load Complete / Load Failed / No Save Found |
| Load Complete | 로드 성공 | Idle |
| Load Failed | 파일 손상·역직렬화 실패 | Idle (Edge Cases의 손상 복구 절차로 진입) |
| No Save Found | 최초 실행(파일 없음) | Idle (빈 상태로 시작, #14가 기본값 초기화) |
| Saving | 소비 시스템의 저장 요청 | Retrying(1차 타임아웃 시) 또는 Save Complete |
| Retrying | 타임아웃 후 재시도 대기(백오프) | Saving(재시도 실행) 또는 Save Failed(3회 모두 소진) |
| Save Complete | 원자적 교체 성공 | Idle |
| Save Failed | 3회 시도 모두 소진(총 16500ms) — **터미널 상태, 1차 타임아웃만으로는 도달하지 않는다** | Idle (소비 시스템에 실패 신호 전달) |

**Loading 중 저장 요청**: `Loading` 상태에서 저장 요청이 도착하면(예: 로드 완료 전 화면에서 설정 변경) 요청은 `SAVE_LOCK_QUEUE_MAX` 큐에 즉시 들어가지 않고, `Load Complete`/`Load Failed`/`No Save Found` 중 하나로 전이한 뒤 처리된다 — 로드 미완료 상태에서 병행 저장은 허용하지 않는다.

## Formulas

이 시스템은 데미지·성장 같은 게임플레이 공식을 소유하지 않는 순수 인프라 시스템이다. 대신 이 시스템의 동작을 "잘 명세되고 테스트 가능하게" 만드는 **정량적 운영 예산과 임계값**을 여기서 확정한다. 아래 5개 값은 QA가 실측으로 pass/fail을 판정할 수 있는 기준선이며, `#14 영구 진행`·`#23 설정`이 저장하는 섹션 데이터의 실제 스키마와 무관하게 이 시스템 스스로 지켜야 하는 계약이다.

**① 세이브 파일 크기 예산 (`SAVE_FILE_SIZE_BUDGET_BYTES`)**

| 심볼 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `save_size_actual` | int (bytes, 런타임 측정) | 0 이상 | 저장 직전 전 섹션을 직렬화한 실제 바이트 수 |
| `SAVE_FILE_SIZE_WARN_BYTES` | int (상수) | 131072 (128 KB) 고정 | 예산의 50% — 초과 시 실패는 아니지만 조기 경보 |
| `SAVE_FILE_SIZE_BUDGET_BYTES` | int (상수) | 262144 (256 KB) 고정 | 최대 허용 크기 — 초과 시 저장 자체를 실패로 처리 |

`save_size_actual > SAVE_FILE_SIZE_BUDGET_BYTES`는 정상적인 스코프 증가로 보지 않고 데이터 이상(예: 배열 무한 증가 버그)으로 간주해 저장을 거부한다. `#14 영구 진행`이 제공한 실측 예상치(Full Vision 동료 20명 + floor + settings ≈ 0.9KB, `#14 영구 진행` 소유 데이터 기준— 이 시스템은 그 내용을 모르며 총 바이트 수만 사용) 대비 약 290배 여유 — 실제 브라우저 쿼터 고갈 방지용이 아니라 버그 조기 발견용 안전핀. **재검토 트리거**: 스키마에 새 대용량 섹션(예: 런 히스토리 로그, 클라우드 세이브 페이로드)이 추가되면 이 상수를 재검토한다.

**② 저장 쓰기 타임아웃 (`SAVE_WRITE_TIMEOUT_MS`)**

| 심볼 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `t_elapsed` | int (ms, 런타임 측정) | 0 이상 | 저장 요청 시작부터 확인 신호까지 경과 시간 |
| `SAVE_WRITE_TIMEOUT_MS` | int (상수) | 5000 (5초) 고정 | 확인 신호를 기다리는 최대 시간 |

`t_elapsed`가 5000ms에 닿으면 무조건 저장 실패(타임아웃) 확정 — 무한 대기 없음. 데스크톱 I/O에는 넉넉하고, 웹 빌드의 비동기 동기화 지연(Core Rule 6)을 흡수할 여유를 준 값.

**③ 저장 실패 재시도 정책 (`SAVE_RETRY_MAX_ATTEMPTS`)**

| 심볼 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `attempt_n` | int | 1 ~ 3 | 시도 회차 (최초 1회 + 재시도 2회) |
| `SAVE_RETRY_MAX_ATTEMPTS` | int (상수) | 2 고정 | 최초 시도 실패 후 재시도 허용 횟수 |
| `retry_n` | int | 1 ~ 2 | 재시도 회차 (`attempt_n`과 별개 — 재시도만 카운트, `delay()`의 입력) |
| `delay(retry_n)` | int (ms) | `500 × 2^(retry_n-1)` | `retry_n`번째 재시도 전 대기 (지수 백오프). `retry_n`은 1~2만 유효 — `delay(3)`은 존재하지 않는다(3회차는 마지막 시도이며 그 이후 재시도가 없음) |

3회 모두 실패 시 자동 재시도 중단, "저장 실패" UI 노출(위 States and Transitions의 `Save Failed`는 이 시점에만 도달하는 터미널 상태). 최악 총 대기 = `5000(attempt_n=1) + 500(delay(retry_n=1)) + 5000(attempt_n=2) + 1000(delay(retry_n=2)) + 5000(attempt_n=3) = 16500ms` — QA의 "저장 실패 표시까지 최대 대기 시간" 테스트 기준.

**④ 로드 시 손상 감지 기준 (`is_save_corrupted`)**

| 검사 항목 | 판정 기준 |
|-----------|-----------|
| 역직렬화 결과 | 파싱 함수가 에러 반환 |
| 최상위 타입 | Dictionary가 아님 |
| `schema_version` 존재 여부 | 필드 부재 또는 non-int |
| `schema_version` 값 유효성 | 1 미만 |
| 파일 크기 | `save_size_actual == 0` |

5개 검사의 **논리합(OR)** — 하나라도 참이면 즉시 손상 확정, 회색지대 없음. Atomic write(Core Rule 4)가 정상 작동한다면 발생하지 않아야 하나, **파일 크기 0 체크는 devtools 수동 편집 같은 외부 요인만이 아니라 Open Question #2(웹 익스포트 IndexedDB 쓰기 동기화 미검증)의 직접적인 실패 모드일 수 있다** — atomic write의 "완료 확인"이 실제 디스크 반영 이전에 신호될 가능성이 아직 검증되지 않았기 때문. ADR 완료 전까지는 이 체크를 "외부 요인 의심"이 아니라 "플랫폼 미검증 리스크의 방어선"으로 취급한다.

**⑤ 동시 저장 요청 잠금 (`SAVE_LOCK_QUEUE_MAX`)**

| 심볼 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `is_save_in_progress` | bool | true/false | 저장 처리 중 여부 |
| `SAVE_LOCK_QUEUE_MAX` | int (상수) | 1 고정 | 대기 큐 최대 깊이 |

**큐 저장 시점 (2026-07-26 리비전 — 리뷰에서 지적된 데이터 유실 가능 모호성 해결)**: 큐에 대기 중인 저장 요청은 **enqueue 시점의 데이터 스냅샷을 들고 있지 않는다** — 대기열의 저장이 실제로 실행되는 시점(Saving 상태 진입 직전)에 소비 시스템의 **현재 최신 상태를 다시 조회**해 저장한다. 따라서 큐가 가득 찬 상태에서 3번째 요청이 드롭되어도, 대기 중이던 2번째 요청이 실행될 때 이미 3번째 요청이 반영하려던 최신 상태(예: 새로 해금된 동료)를 포함해서 저장하므로 데이터 유실이 없다. (자동저장은 여전히 MVP 범위 밖 — 이 재조회는 "이미 큐에 들어온 요청의 실행 시점"에만 적용되며, 아무 저장 요청도 없는 상태에서 상태 변경을 자동으로 저장하지 않는다.)

atomic write는 단일 writer 전제 — 모바일 터치 더블탭 같은 동시 저장 요청 시 레이스 방지. 큐 1개는 "저장 중 눌림"이라는 유효한 의도를 완전히 버리지 않고 이어서 처리하기 위함.

## Edge Cases

- **최초 실행(세이브 파일 없음)**: `No Save Found` 상태로 진입 — 에러 아님. 빈 상태로 시작하며 `#14 영구 진행`이 기본값(해금 동료 0명 + 기본 동료 1명)을 초기화한다.

- **로드 시 손상 감지 (`is_save_corrupted = true`)**: 손상된 파일을 `[filename].corrupted.bak`으로 백업 이동 후 `No Save Found`로 취급해 새 세이브로 초기화. `push_error("Save file corrupted, backed up and reset")` 로그. 플레이어 알림 UI는 `#20 UI/HUD` 소유 — 이 시스템은 손상 이벤트 신호만 발신한다.

- **`schema_version`이 현재 기대치보다 높은 경우** (예: 개발 중 새 빌드로 저장한 파일을 구버전 빌드로 로드): 손상과 동일하게 취급 — 백업 후 새 세이브로 초기화. 마이그레이션 대상이 아니라 안전 실패로 처리한다.

- **`schema_version`이 낮은 경우(구버전 마이그레이션)**: MVP는 `schema_version = 1` 고정이라 이 케이스는 아직 발생하지 않는다. Full Vision에서 버전이 늘어날 때 마이그레이션 체인 설계가 필요 — 지금은 미해결(Open Questions 참조).

- **저장 요청 큐가 가득 찬 상태에서 추가 요청**: `SAVE_LOCK_QUEUE_MAX`(1) 초과분은 무시(드롭)한다. 플레이어에게 실패 알림 없음 — 대기 중인 저장은 **실행 시점에 최신 상태를 재조회**하므로(Formulas ⑤ 참조) 드롭된 요청이 반영하려던 변경사항도 함께 저장되어 데이터 유실이 없다.

- **저장 파일이 `SAVE_FILE_SIZE_BUDGET_BYTES`(256KB) 초과**: 저장을 거부하고 `push_error` + 소비 시스템에 실패 신호. 게임은 계속 진행하며 마지막으로 성공한 세이브 상태를 유지한다 — 크래시 없음.

- **브라우저가 로컬 저장소를 차단한 경우(시크릿 모드 등)**: 이 시스템은 이 상황을 별도로 감지하지 않는다 — 모든 저장 시도가 `SAVE_WRITE_TIMEOUT_MS` 경과 후 실패로 수렴하고, 재시도 정책(③)을 거쳐 "저장 실패" UI가 지속 노출된다.

## Visual/Audio Requirements

이 시스템은 시각 자산을 소유하지 않는다 — 실제 UI 렌더링은 `#20 UI/HUD`가 담당한다. 이 시스템의 책임은 UI가 반응할 수 있는 상태 신호(저장 성공/실패/진행 중, 손상 복구 발생)를 명확히 제공하는 것뿐이다.

아트 바이블 관련: 저장 실패·손상 복구 알림은 섹션 1 원칙 3(UI는 전장을 가리지 않는다 — 하단 25%/테두리 16px 내 배치, 채도 30 이하 청회색)을 따르는 일반 시스템 알림으로 취급한다. 위협홍(`#C0392B`, 적 전용 시맨틱)을 재사용하지 않는다 — 시맨틱 충돌 방지를 위해 별도 회색/청회색 계열 오류 색상을 `#20 UI/HUD` GDD에서 확정해야 한다.

오디오: 이 시스템은 오디오 필드를 갖지 않는다 — `#21 오디오`가 저장 실패/손상 이벤트 신호를 구독해 알림음을 재생한다.

## UI Requirements

이 시스템은 직접 UI를 렌더링하지 않지만, 아래 3개 사용자 대면 신호는 `#20 UI/HUD`가 반드시 처리해야 하는 실제 요구사항이다:

1. **저장 실패 알림**: 재시도 소진 후(최대 16.5초) 최종 실패 시 플레이어에게 명확히 표시 — 조용히 실패시키지 않는다 (Player Fantasy의 "신뢰"가 걸린 지점).
2. **손상 복구 알림**: 로드 시 손상 감지로 세이브가 초기화된 경우, "이전 진행 상황을 불러올 수 없어 새로 시작합니다" 같은 명확한 고지 — 조용히 리셋하면 플레이어가 소실을 자기 실수로 오인할 수 있음.
3. **저장 중 상태 미표시(의도적 침묵)**: 저장은 순간적으로 일어나며 성공 시 별도 토스트가 불필요할 수 있음(실패 시에만 표시) — 정확한 패턴은 `/ux-design`에서 결정.

📌 **UX Flag — 로컬 세이브**: 이 시스템은 UI 요구사항을 가진다. Pre-Production 단계에서 `/ux-design`으로 저장 실패·손상 복구 알림 UX 스펙을 작성할 것 — 이후 스토리는 이 GDD가 아니라 `design/ux/[screen].md`를 인용해야 한다.

## Acceptance Criteria

**핵심 규칙 커버리지**

1. (핵심 규칙 1 – 섹션 기반 제네릭 API) GIVEN 저장 시스템이 초기화된 상태에서, WHEN `"companion_unlocks"`와 `"settings"` 두 섹션에 각각 임의의 데이터 blob을 저장 요청하면, THEN 시스템은 두 섹션의 내용을 해석/검증하지 않고 그대로 직렬화하여 저장하며, 이후 섹션 이름으로 조회 시 저장한 원본 blob과 완전히 동일한 데이터를 반환한다.

2. (핵심 규칙 2 – 명시적 트리거만) GIVEN 세이브 대상 데이터가 마지막 저장 이후 변경된 상태에서, WHEN 플레이어가 명시적으로 저장을 요청하지 않은 채 임의의 시간(예: 5분)이 경과하면, THEN 시스템은 Saving 상태로 자동 전이하지 않고 세이브 파일은 갱신되지 않는다.

3. (핵심 규칙 3 – 단일 파일·다중 섹션) GIVEN `"companion_unlocks"`와 `"settings"` 두 섹션을 저장한 상태에서, WHEN `user://`에 생성된 세이브 파일을 확인하면, THEN 세이브 파일은 정확히 1개만 존재하고 그 안에 두 섹션의 데이터가 모두 포함되어 있다(섹션별 파일이 별도 생성되지 않는다).

4. (핵심 규칙 4 – 원자적 쓰기) GIVEN 기존 세이브 파일이 존재하는 상태에서, WHEN 새 저장 요청의 임시 파일 쓰기가 완료되어 기존 파일과 swap되기 *이전* 시점에 프로세스가 강제 종료되면, THEN 재시작 후 기존 세이브 파일은 손상 없이 그대로 로드 가능하다. **테스트 가능성 노트**: GUT은 실제 프로세스 강제종료를 시뮬레이션하는 기능이 없으므로, 구현은 `_write_temp()`와 `_swap()`을 별도로 호출 가능한 단계로 노출해야 한다 — 테스트는 `_write_temp()`만 호출하고 `_swap()`을 호출하지 않은 채로 두어 "swap 이전 중단"을 시뮬레이션하고, 기존 파일이 원본과 바이트 단위로 동일한지 검증한다.

5. (핵심 규칙 5 – schema_version 필드) GIVEN 임의의 섹션 데이터를 저장한 상태에서, WHEN 저장된 파일을 최상위 레벨에서 파싱하면, THEN `schema_version` 필드가 int 타입으로 존재하며 값은 1이다.

6. (핵심 규칙 6 – 명시적 성공/실패 반환, UI 대기) GIVEN 저장 요청이 발생했고 temp file 쓰기+swap의 완료 확인이 아직 시스템으로부터 신호되지 않은 상태에서, WHEN UI가 저장 결과를 표시하려 하면, THEN UI는 "저장됨" 메시지를 표시하지 않으며, 시스템으로부터 명시적 성공 신호를 수신한 시점에만 표시한다.

**공식/임계값 커버리지**

7. (공식 1 – 하드 캡) GIVEN 저장하려는 데이터 총 크기가 `SAVE_FILE_SIZE_BUDGET_BYTES`(262144바이트)를 초과하는 상태에서, WHEN 저장을 요청하면, THEN 저장은 거부되고 Save Failed로 전이하며 `push_error`가 로깅된다.

8. (공식 1 – 경고 임계값) GIVEN 저장하려는 데이터 총 크기가 `SAVE_FILE_SIZE_WARN_BYTES`(131072바이트) 이상 262144바이트 이하인 상태에서, WHEN 저장을 요청하면, THEN 경고가 로깅되지만 저장은 Save Complete로 정상 성공한다.

9. (공식 2 – 쓰기 타임아웃) GIVEN 저장 요청이 진행 중인 상태에서, WHEN `SAVE_WRITE_TIMEOUT_MS`(5000ms) 이내에 완료 확인 신호가 도착하지 않으면, THEN 해당 시도는 timeout으로 실패 판정된다.

10. (공식 3 – 재시도 및 총 소요시간) GIVEN 모든 저장 시도가 매번 5000ms 타임아웃으로 실패하는 상태에서, WHEN 최초 시도가 실패하면, THEN `SAVE_RETRY_MAX_ATTEMPTS`(2)에 따라 총 3회 시도가 이루어지고, 1차 재시도 전 지연은 500ms, 2차 재시도 전 지연은 1000ms(`delay(retry_n)=500×2^(retry_n-1)`)이며, 최초 요청부터 최종 "Save Failed" UI 표시까지 총 소요시간은 16500ms(5000×3+500+1000)이다. **테스트 가능성 노트**: 실시간 16.5초를 그대로 기다리는 테스트는 피한다 — 타임아웃/백오프 로직은 주입 가능한 clock/timer 추상화를 통해 구현하여, 테스트가 모의(mock) 시간 진행으로 밀리초 단위로 실행되도록 한다.

11. (공식 4 – 손상 판정 a: 역직렬화 오류) GIVEN 세이브 파일이 역직렬화 중 파싱 오류를 일으키는 상태에서, WHEN 로드를 시도하면, THEN `is_save_corrupted`는 true로 판정된다.

12. (공식 4 – 손상 판정 b: 최상위 타입) GIVEN 세이브 파일의 최상위 구조가 Dictionary가 아닌 상태(예: 배열/문자열)에서, WHEN 로드를 시도하면, THEN `is_save_corrupted`는 true로 판정된다.

13. (공식 4 – 손상 판정 c: schema_version 누락/타입 불일치) GIVEN 세이브 파일에 `schema_version` 필드가 없거나 값이 int가 아닌 상태에서, WHEN 로드를 시도하면, THEN `is_save_corrupted`는 true로 판정된다.

14. (공식 4 – 손상 판정 d: schema_version 범위) GIVEN 세이브 파일의 `schema_version` 값이 1 미만(예: 0)인 상태에서, WHEN 로드를 시도하면, THEN `is_save_corrupted`는 true로 판정된다.

15. (공식 4 – 손상 판정 e: 파일 크기 0) GIVEN 세이브 파일의 크기가 0바이트인 상태에서, WHEN 로드를 시도하면, THEN `is_save_corrupted`는 true로 판정된다.

16. (공식 5 – 큐 최대치) GIVEN 저장 요청 1건이 이미 Saving 중이고 대기열에 1건이 큐잉되어 있는 상태(`SAVE_LOCK_QUEUE_MAX`=1)에서, WHEN 3번째 저장 요청이 발생하면, THEN 3번째 요청은 조용히 드롭되며 실패로 표시되지 않는다.

**엣지 케이스 커버리지 (중복되지 않는 항목만)**

17. (엣지 케이스 1 – 최초 실행) GIVEN `user://`에 세이브 파일이 존재하지 않는 상태에서, WHEN 게임을 부팅하면, THEN 시스템은 No Save Found로 전이하고 에러로 처리되지 않는다(`push_error` 없음). (이후 `#14 영구 진행`이 자신의 기본값으로 초기화하는지는 `#14`의 AC 범위이며, 이 시스템은 "빈 상태로 시작"이라는 신호만 제공한다.)

18. (엣지 케이스 2 – 손상 세이브 처리) GIVEN `is_save_corrupted`가 true로 판정된 세이브 파일이 존재하는 상태에서, WHEN 로드를 시도하면, THEN 원본 파일은 `[filename].corrupted.bak`으로 백업되고 시스템은 No Save Found로 처리되며 `push_error`가 로깅된다.

19. (엣지 케이스 3 – 상위 schema_version) GIVEN 세이브 파일의 `schema_version` 값이 현재 빌드가 인식하는 값보다 높은 상태(예: 2)에서, WHEN 로드를 시도하면, THEN 손상 세이브와 동일하게 `.corrupted.bak` 백업 후 No Save Found로 전이한다.

20. (엣지 케이스 6 – 256KB 초과 시 게임 지속) GIVEN 마지막으로 성공한 세이브가 존재하고 게임이 정상 실행 중인 상태에서, WHEN 새 저장 시도가 256KB 초과로 거부되면, THEN 게임은 크래시 없이 계속 실행되고, 메모리상 게임 상태는 유지되며, 기존 세이브 파일은 덮어써지지 않고 마지막 성공 세이브 상태 그대로 남는다.

**상태 전이 보완 (해피 패스 – 실패 케이스만으로는 커버되지 않는 정상 흐름)**

22. GIVEN 유효한 크기의 섹션 데이터가 있는 상태에서, WHEN 저장을 요청하고 temp file 쓰기 및 기존 파일과의 swap이 성공적으로 완료되면, THEN 시스템은 Save Complete로 전이하고 호출자에게 성공 신호를 반환한다.
