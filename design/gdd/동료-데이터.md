# 동료 데이터 (Companion Data)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 발견의 기쁨 / 성장은 영원하다

## Overview

동료 데이터 시스템은 바람의 탑 게임 내 모든 동료(Companion)의 **정적 블루프린트**를 정의하는 Foundation 레이어 시스템이다. 각 동료의 이름·초상화 ID·클래스 타입·기본 스탯(HP/공격력/방어력/속도)·스킬 참조·히든 여부·해금 조건 등 "런에 상관없이 변하지 않는 정보"를 담은 데이터 구조체이며, 총 9개 하위 시스템의 공통 기반으로 동작한다. 런 내 동적 상태(현재 HP, 버프 등)는 이 시스템이 아닌 #13 런 상태 관리가 소유하고, 해금 여부는 #14 영구 진행이 소유한다. 플레이어 관점에서 동료 데이터는 "히든 동료를 처음 발견하는 순간" 화면에 즉각 나타나는 이름·고유 컬러·짧은 사연의 원천이다 — 이 데이터가 없으면 "발견의 기쁨" 필라 자체가 성립하지 않는다. MVP에서는 동료 4명(기본 1명 + 히든 3명)을 정의하며, Full Vision에서 최대 20명까지 확장된다.

## Player Fantasy

"이 동료... 내가 처음 찾은 거다."

히든 동료를 발견하는 순간은 우연이 아닌 탐색의 보상이다. 플레이어는 동료 데이터가 무엇인지 알 필요가 없다 — 단지 이름이 뜨고, 고유한 따뜻한 컬러가 어두운 던전에 번지고, 두 줄의 사연이 눈에 들어오는 그 순간을 경험할 뿐이다.

동료 데이터 시스템이 만드는 감각:
- **수집의 쾌감**: 도감에 빈칸이 채워지는 느낌. "아직 못 찾은 동료가 몇 명이나 더 있을까?"
- **애착 형성의 씨앗**: 이름과 짧은 사연 하나로 동료가 "유닛"이 아닌 "캐릭터"가 된다.
- **성장의 물리적 증거**: 런이 끝나도 이 동료는 내 로스터에 남는다. 실패한 런이 아무것도 아닌 런이 되지 않는 이유.

플레이어는 "동료 데이터 시스템"을 경험하는 것이 아니다. 처음 만나는 동료의 이름을 기억하고, 그 동료와 함께 다음 런을 시작하고 싶은 마음이 생기는 것을 경험한다.

## Detailed Rules

### Core Rules

**CompanionData 스키마** (GDScript — `CompanionData extends Resource`):

```gdscript
class_name CompanionData
extends Resource

# 식별자
@export var id: String            # 고유 ID (예: "warrior_01", "hidden_mage_02")
@export var name: String          # 표시 이름 (예: "검사 아이라")
@export var description: String   # 1~2줄 사연
@export var class_type: String    # 아키타입 태그: "tank" | "dealer" | "balance" | "support" — #7 적 AI, #8 시너지가 참조

# 시각
@export var portrait_id: String    # 초상화 스프라이트 ID
@export var color_accent: Color    # 고유 컬러 포인트 — 아트 바이블 H:280°~H:130° 범위 준수. 네이티브 Color 타입 사용 (hex 문자열 금지 — 소비 시스템마다 파싱/폴백을 재구현하지 않도록)

# 기본 스탯 (런과 무관하게 고정)
@export var base_hp: int    # 기본 최대 HP — 범위 60~150, 단 0 이하는 로드 자체를 거부 (Edge Cases 참조)
@export var base_atk: int   # 기본 공격력
@export var base_def: int   # 기본 방어력
@export var base_spd: int   # 기본 속도 (턴 순서 결정)

# 스킬
@export var skill_id: String  # SkillData 리소스 참조 ID (MVP: 정확히 1개)

# 해금
@export var is_hidden: bool = false       # true = 히든 동료 (기본값 false)
@export var unlock_condition_id: String   # #9 히든 트리거 참조 ID ("" = 기본 동료)
```

`class_type`은 밸런스 계산에 개입하지 않는 순수 태그다 — 스탯 자체로 아키타입이 자연히 구분되지 않는 경우에도(예: 딜러/지원 스탯이 근접), #7/#8이 스탯을 역산 추론하지 않고 이 필드로 직접 분기할 수 있게 한다.

**SkillData 스키마** (별도 리소스 — 이 GDD에서 구조 정의, 스킬 GDD에서 상세화):

```gdscript
class_name SkillData
extends Resource

@export var id: String
@export var name: String
@export var description: String
@export var target_type: String = "enemy"   # "enemy" | "self" | "ally" | "all_allies" — #1 턴제 전투가 적용 대상 결정에 사용
@export var damage_multiplier: float = 1.0  # 기본 공격력 대비 배율. 유효 범위 0.5~3.0 (target_type="enemy"에만 적용)
@export var heal_multiplier: float = 0.0    # 대상의 base_hp 대비 회복 배율. 0 = 회복 없음. 유효 범위 0.0~1.0 (target_type="self"|"ally"|"all_allies"에서만 사용)
@export var effect_id: String               # 상태이상 참조 ID ("" = 없음) — #12 상태이상 참조. target_type에 따라 버프(ally 대상)든 디버프(enemy 대상)든 동일 필드로 표현
@export var cost_sp: int = 0                # 스킬 포인트 소모량. 유효 범위 0~5
```

`target_type="ally"`/`heal_multiplier` 조합으로 "지원(support)" 아키타입이 실제로 힐/버프를 수행할 수 있다 — #12 상태이상은 이미 버프(방어 강화)를 지원하므로, 이 필드는 그 버프를 아군에게 겨냥하는 역할만 추가한다.

**파일 위치 및 로딩 소유권:**
- CompanionData: `assets/data/companions/[id].tres`
- SkillData: `assets/data/skills/[skill_id].tres`
- 로딩·중복 검증·정렬은 `CompanionRegistry` 오토로드 싱글톤이 소유한다 (이 GDD는 데이터 계약만 정의하며, 레지스트리 구현은 별도 구현 GDD/ADR에서 상세화한다). `CompanionRegistry`는 `assets/data/companions/`의 파일 목록을 **파일명 오름차순(알파벳/유니코드 코드포인트 순)으로 정렬한 뒤** 순서대로 로드한다 — Godot의 디렉토리 스캔 순서가 플랫폼(에디터/웹 익스포트)마다 다를 수 있으므로, 정렬은 이 문서가 명시하는 필수 규칙이다. 동일한 로직(폴더 열거 → 정렬 → 로드 → 중복 검사)은 `#11 적 데이터`의 `EnemyRegistry`도 필요로 하므로, 공용 유틸리티 함수로 구현해 두 레지스트리가 공유한다(로직 중복 방지 — 각 레지스트리는 폴더 경로/타입만 다른 얇은 wrapper).

### States and Transitions

동료 데이터 자체는 **불변(immutable)** — 상태 전이 없음. 동료 라이프사이클은 다른 시스템이 관리:

| 상태 | 관리 시스템 | 설명 |
|------|-------------|------|
| 미발견 | #14 영구 진행 | 히든 동료, 도감 미등록 |
| 해금됨 | #14 영구 진행 | 발견 후 영구 로스터 추가 |
| 파티 편성 중 | #15 파티 구성 | 현재 런에서 선택된 상태 |
| 전투 중 | #13 런 상태 관리 | 현재 HP, 상태이상 — 이 시스템은 소유하지 않음 |

## Formulas

이 시스템은 계산 공식이 없는 순수 데이터 시스템이다. 대신 #6 전투 공식이 입력값으로 사용할 **스탯 범위**를 여기서 확정한다.

**스탯 범위 정의:**

| 스탯 | 심볼 | 타입 | 범위 | 설명 |
|------|------|------|------|------|
| 기본 최대 HP | `base_hp` | int | 60 ~ 150 | 낮을수록 딜러, 높을수록 탱커 성향 |
| 기본 공격력 | `base_atk` | int | 10 ~ 30 | 기본 공격 데미지의 원천 |
| 기본 방어력 | `base_def` | int | 5 ~ 20 | 받는 데미지 감소 |
| 기본 속도 | `base_spd` | int | 1 ~ 10 | 높을수록 먼저 행동 (턴 순서) |

**MVP 4명 예시 배분 (참고용 — 실제 캐릭터 미확정):**

| 역할 유형 | class_type | base_hp | base_atk | base_def | base_spd | 스킬 예시 |
|-----------|------------|---------|----------|----------|----------|-----------|
| 탱커 성향 | `"tank"` | 150 | 12 | 20 | 3 | target_type="enemy", damage_multiplier 낮음 |
| 밸런스 (기본 동료) | `"balance"` | 100 | 18 | 12 | 6 | target_type="enemy" |
| 딜러 성향 | `"dealer"` | 70 | 28 | 7 | 8 | target_type="enemy", damage_multiplier 높음 |
| 지원 성향 | `"support"` | 80 | 14 | 10 | 9 | target_type="ally", heal_multiplier > 0 또는 effect_id="defense_up" (아군 대상 버프) |

`class_type`이 태그이므로 스탯만으로 "지원"이 구분되지 않아도(딜러와 근접한 스탯이어도) 무방하다 — 실제 역할 구분은 태그 + 스킬의 `target_type`/`heal_multiplier` 조합이 만든다.

> 이 범위는 #6 전투 공식 GDD의 데미지 계산 입력 범위가 된다. 전투 공식 GDD 작성 전에 변경이 필요하면 이 GDD를 먼저 수정한다.

## Edge Cases

- **기본 동료의 해금 조건이 없는 경우**: `is_hidden = false`, `unlock_condition_id = ""` — 런 시작 시 파티 선택 화면에 항상 표시. `#14 영구 진행`은 이 동료를 "기본 해금" 상태로 초기화한다.

- **이미 해금된 히든 동료를 같은 런에서 다시 발견한 경우**: `#3 동료 해금`이 `#14 영구 진행`을 조회 → 이미 등록 확인 → 해금 스킵. "이미 동료가 되어 있어요" 메시지 표시. CompanionData는 변경 없음.

- **`portrait_id`가 비어 있거나 해당 스프라이트가 없는 경우**: `portrait_id = ""` 또는 파일 미존재 시 fallback 초상화 스프라이트(`portrait_missing.png`) 사용. null 참조 에러 없이 게임 진행 유지.

- **같은 `id`를 가진 `.tres` 파일이 2개 이상 로드된 경우**: `CompanionRegistry`가 `assets/data/companions/`의 파일 목록을 **파일명 오름차순으로 정렬한 뒤** 순서대로 로드한다 — "첫 번째로 로드된 데이터"는 이 정렬 순서 기준이며, 플랫폼(에디터/웹 익스포트)에 따라 달라지는 디렉토리 스캔 순서에 의존하지 않는다. 정렬 후 첫 번째가 아닌 나머지는 `push_error("Duplicate companion id: [id]")` 출력 후 무시. 빌드 검증 도구가 이를 경고로 잡아야 한다(Acceptance Criteria 참조).

- **`skill_id`가 존재하지 않는 스킬을 참조하는 경우 (런타임 세이프티넷)**: 이 폴백 로직은 `#1 턴제 전투`가 소유한다 — 이 GDD는 데이터 계약만 명시: SkillData 로드 실패 감지 시 `skill_id = "skill_basic_attack"`(기본 공격)으로 fallback, `push_warning("Missing skill: [skill_id], falling back to basic_attack")` 로그 출력. 이와 별도로, 빌드 검증 도구가 **로드 이전에** `skill_id` 참조 무결성을 정적으로 검사해 존재하지 않는 참조를 경고로 잡는다 (중복 `id` 검증과 동일한 빌드 도구가 담당, Acceptance Criteria 참조) — 런타임 폴백은 이 정적 검사를 놓친 경우의 최후 방어선이다.

- **`base_hp`가 0 이하인 경우 (크래시 등급 — 클램핑 대상 아님, 로드 거부 대상)**: `base_hp ≤ 0`은 밸런스 튜닝 범위 문제가 아니라 전투 시작 즉시 패배를 유발하는 게임 루프 크래시다. 로드 시 `push_error("Invalid base_hp for [id]: must be > 0")` 출력 후 **해당 CompanionData는 로드하지 않는다** (게임에 등록되지 않음 — 아래 "범위 초과" 케이스와 달리 값 그대로 사용하지 않는다).

- **그 외 스탯 값이 정의된 범위를 초과하는 경우** (`base_atk`/`base_def`/`base_spd`가 범위 밖이거나, `base_hp`가 150 초과인 경우 등 — **0 이하 `base_hp`는 제외, 위 항목 참조**): 데이터 오류로 간주. 로드 시 `push_warning` 출력하되 게임은 해당 값 그대로 사용 (강제 클램핑 없음 — 디자이너가 범위 외 값을 의도적으로 테스트할 수 있어야 함). `SkillData`의 `damage_multiplier`(0.5~3.0), `heal_multiplier`(0.0~1.0), `cost_sp`(0~5)도 동일 정책 — 범위 밖이어도 `push_warning`만 출력하고 값은 그대로 사용한다.

## Dependencies

### Upstream Dependencies (이 시스템이 의존하는 것)

없음. Foundation 레이어 — 다른 어떤 시스템에도 의존하지 않는다.

### Downstream Dependents (이 시스템에 의존하는 것)

| 시스템 | 의존 유형 | 기대하는 인터페이스 |
|--------|-----------|---------------------|
| #1 턴제 전투 | **Hard** — 없으면 전투 불가 | `base_hp`, `base_atk`, `base_def`, `base_spd`, `skill_id` |
| #3 동료 해금 | **Hard** — 없으면 해금 연출 불가 | `id`, `name`, `description`, `portrait_id`, `color_accent`, `is_hidden` |
| #4 장비 | **Hard** — 보정 기준값 없음 | `base_atk`, `base_def` |
| #6 전투 공식 | **Hard** — 입력 범위 정의 불가 | 스탯 범위 (Formulas 섹션 참조) |
| #7 적 AI | **Soft** — AI 동작은 하되 타겟 우선순위 단순화됨 | `base_atk`, `base_spd`, `class_type` |
| #8 시너지 | **Hard** — 조합 계산 불가 | `id`, `skill_id`, `class_type` |

## Acceptance Criteria

1. **GIVEN** 게임이 시작될 때, **WHEN** `CompanionRegistry`가 `assets/data/companions/`의 파일들을 정렬된 순서로 로드하면, **THEN** MVP 4명 동료가 모두 로드되어 `push_error`/`push_warning` 호출 횟수가 0이고, 4개 `CompanionData` 인스턴스 모두 non-null이며 각각 고유한 `id`를 가진다.

2. **GIVEN** 기본 동료 (`is_hidden = false`, `unlock_condition_id = ""`), **WHEN** `CompanionRegistry`에서 이 동료의 `CompanionData`를 조회하면, **THEN** `is_hidden == false`가 반환된다. (파티 선택 화면에 실제로 표시되는지는 `#15 파티 구성`의 AC 범위이며 여기서 보장하지 않는다.)

3. **GIVEN** 히든 동료 (`is_hidden = true`)이고 아직 해금되지 않은 상태, **WHEN** 파티 선택 화면이 이 동료를 렌더링하면, **THEN** 목록에서 "???" 잠금 카드로 항상 표시되고 선택이 불가능하다. (구 사양의 "표시 안 함" 대안은 폐기 — 두 구현이 동시에 통과하는 모호한 OR였음.)

4. **GIVEN** 빌드 검증 도구가 실행될 때, **WHEN** 어떤 CompanionData의 `skill_id`가 존재하지 않는 SkillData를 참조하면, **THEN** 빌드 단계에서 경고가 출력된다. (런타임 폴백은 Edge Cases의 별도 세이프티넷이며 이 AC의 대상이 아니다.)

5. **GIVEN** 동일한 `id`를 가진 CompanionData 파일 2개, **WHEN** `CompanionRegistry`가 파일명 오름차순 정렬 후 로드하면, **THEN** 정렬 순서상 첫 번째 파일만 사용되고 `push_error`가 출력되며 게임이 중단되지 않는다. (테스트는 이름이 알려진 두 고정 fixture 파일로 정렬 결과를 검증한다.)

6. **GIVEN** `base_hp ≤ 0`을 가진 CompanionData, **WHEN** `CompanionRegistry`가 이를 로드하려 하면, **THEN** `push_error`가 출력되고 해당 CompanionData는 로드되지 않는다 (게임에 등록되지 않음). (데미지가 0/음수가 되지 않는다는 보장 자체는 `#6 전투 공식`이 소유하며 이 시스템의 AC가 아니다 — 구 AC6은 이 문서가 증명할 수 없는 주장이었으므로 대체됨.)

7. **GIVEN** `portrait_id`가 비어 있는 CompanionData, **WHEN** 초상화 로더가 fallback 스프라이트(`portrait_missing.png`)를 요청하면, **THEN** non-null `Texture2D`가 반환된다. (실제 화면에 정상적으로 그려지는지는 Visual/UI 스토리 타입 — `.claude/docs/coding-standards.md` 기준 ADVISORY 등급이며 스크린샷으로 별도 확인한다.)
