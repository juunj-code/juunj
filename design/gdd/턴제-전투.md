## Overview

턴제 전투 시스템은 바람의 탑의 전투 흐름 전체를 오케스트레이션하는 Feature 레이어 시스템이다. 전투 시작 시 #13 런 상태 관리에서 파티·적 상태를 받아, #6 전투 공식이 정한 턴 순서대로 각 유닛의 행동을 진행한다. 플레이어 턴에는 액션·타겟 입력을 받고, 적 턴에는 #7 적 AI에 결정을 위임한다. 데미지 계산은 #6 전투 공식, 상태이상 처리는 #12 상태이상, 결과 저장은 #13 런 상태 관리에 각각 위임한다. 이 시스템은 "게임플레이 수치"를 계산하지 않는다 — 순서를 정하고, 입력을 받고, 결과를 분배하는 지휘자 역할이다.

## Player Fantasy

"이번 턴에 기절 거는 게 맞나, 아니면 독 걸린 애 먼저 처리하는 게 맞나?"

전투는 빠르게 진행돼야 하지만, 각 선택에 무게감이 있어야 한다. 한 턴이 15~30초 안에 끝나고, 전투 하나는 3~5분 내에 마무리된다. 복잡한 메뉴 탐색 없이 탭 두 번(액션 선택 → 타겟 선택)으로 입력이 완료된다.

## Detailed Rules

### 전투 흐름

**구현 패턴 (2026-07-26 리비전 — 리뷰에서 지적된 async 구조 미명시 해결)**: 아래 흐름은 개념 순서일 뿐, 그대로 동기 `while`/`for` 루프로 구현할 수 없다 — "입력 대기" 단계는 Core Rule 1(타임아웃 없음)에 따라 실제 터치 입력까지 무기한 대기해야 하므로, 커스텀 시그널(`await action_selected`, `await target_selected`)에 대한 `await`로 구현한다. 나머지(공식 호출·효과 적용)는 순수 동기 계산이다.

```
전투 시작
  ↓
동료 유닛 base stat 갱신 (2026-07-28 추가 — 장비 반영 연결)
  각 파티원에 대해 #4.get_effective_atk(companion_state) / get_effective_def(companion_state) 호출
  → 전투용 유닛 데이터의 base_atk/base_def에 저장 (장비는 전투 중 변경 불가 — #4 Core Rule 3 — 이므로 전투 시작 시 1회 조회로 충분)
  적 유닛은 #11 EnemyData의 base_atk/base_def 그대로 사용 (장비 없음)
  ↓
턴 순서 계산 (#6 공식 ③)
  ↓
on_round_start():  # 2026-07-26 추가 — 매 라운드 시작 시 명시적으로 실행되는 별도 단계
  턴 순서 재계산 (#6 공식 ③)
  targeted_this_turn = []   # 이전 라운드 타겟 기록 초기화
  ↓
[턴 루프]
  현재 유닛 턴 시작
    → #12: DOT 틱 + 지속시간 감소 + 만료 제거
    → 전투 종료 체크 (#6 공식 ⑤ 호출) — DOT 즉사 포함, 결과(victory/defeat)를 그대로 받아 처리
    → SKIP_TURN 여부 확인
        YES: 턴 스킵 → 다음 유닛
        NO:
          플레이어 유닛: await action_selected, await target_selected (무기한 대기 — Core Rule 1)
          적 유닛: #7 AI에 결정 위임 — `decide_action(enemy, alive_companions, targeted_this_turn)` 호출.
                   `targeted_this_turn`은 이 시스템(#1)이 `on_round_start()`에서 초기화해 소유하는 상태이며
                   (#7 적 AI의 타겟 분산 규칙이 사용), 적 유닛이 타겟을 결정할 때마다
                   이 시스템이 해당 타겟을 `targeted_this_turn`에 추가한다.
    → 액션 실행 (데미지: #6 공식 ①②, 회복: `target_type`이 "self"/"ally"/"all_allies"이고 `heal_multiplier > 0`인 경우 #6 공식 ⑥ — 2026-07-28 추가, 재검토에서 발견된 미구현 회복 경로 수정, 효과: #12 apply_effect)
    → 전투 종료 체크 (#6 공식 ⑤ 호출)
    → SP 회복 (#6 공식 ④: sp += SP_GAIN_PER_TURN)
    → 다음 유닛
  [모든 유닛 턴 완료 → 새 라운드: on_round_start() 재실행]
  ↓
전투 종료 → #13 결과 전달 → #19 씬 전환
```

### 플레이어 입력 프로토콜 (터치 우선)

| 단계 | UI 요소 | 입력 |
|------|---------|------|
| 1. 액션 선택 | 하단 버튼: [기본 공격] [스킬 (SP 부족 시 비활성)] | 탭 |
| 2. 타겟 선택 | 적 유닛 위 선택 하이라이트 | 탭 |
| 3. 확인 | 자동 실행 (타겟 선택 즉시) | — |

취소: 타겟 선택 전에 다른 액션 버튼 탭 → 액션 재선택. 타겟 선택 후 취소 없음 — 빠른 템포 유지.

### 전투 시작 조건 (2026-07-26 리비전 — 존재하지 않는 API 참조 제거)

- `RunManager.state == "EXPLORING"` + 전투 방 진입
- `#13 런 상태 관리`의 전투 진입 절차를 트리거 → `current_enemies` 초기화, `state = "IN_COMBAT"` (`#13`은 이를 명명된 메서드가 아닌 인라인 절차로 소유 — `런-상태-관리.md`의 "전투 진입/종료" 참조. 이 시스템은 그 절차를 시작시키기만 하며, 존재하지 않는 `start_combat()` 메서드를 가정하지 않는다.)
- `SceneManager.go_to(S-05, FADE)`

### 전투 종료 조건 (2026-07-26 리비전 — #6 Formula⑤와의 중복/구식 프레이밍 제거)

이 시스템은 승패 판정 로직을 소유하지 않는다 — 매 HP 차감 직후 `#6 전투 공식` Formula ⑤를 호출하고, 그 결과(victory/defeat)를 그대로 받아 다음 처리만 한다:

| Formula ⑤ 결과 | 처리 |
|-----------------|------|
| victory | `#13 런 상태 관리`의 전투 종료(승리) 절차 트리거 (인라인 절차 — `end_combat()`이라는 명명된 메서드는 존재하지 않음) |
| defeat | `RunManager.end_run(success=false)` 호출 (`#13`의 실제 명명된 API) |

**"동시 발생" 프레이밍 폐기**: 구 버전은 "동시 발생 시 승리 우선"이라고 서술했으나, `#6 전투 공식` Formula ⑤ 리비전에서 이 프레이밍 자체가 부정확함이 확인됐다 — "공격자 피해 → 방어자 피해" 고정 순서 때문에 실제로는 동시 발생이 일어나지 않으며, 공격자 측 승리가 방어자의 반격보다 항상 먼저 확정된다. 이는 우선순위 규칙이 아니라 고정된 적용 순서의 자연스러운 결과다 (`#6` Formula ⑤ 및 AC9 참조).

### Core Rules

1. **입력 없이 진행 없음**: 플레이어 턴에서 입력 없으면 전투 대기 — 타임아웃 없음 (턴제).
2. **턴 순서는 매 라운드 재계산**: 버프로 speed가 변하면 다음 라운드 순서가 바뀐다.
3. **SP 회복은 턴 종료 후**: 행동 완료 후 SP 회복. 해당 턴에 스킬 쓰고 같은 턴에 또 회복되는 구조 아님.
4. **전투 중 씬 전환 없음**: 히든 동료 발견 연출 등 모든 인터럽트는 전투 종료 후 처리.

## Edge Cases

- **파티 전원 기절(SKIP_TURN) 상태**: 기절은 1턴 — 다음 라운드 정상 행동. 모두 기절 중인 라운드는 전체 스킵, 전투 진행 불가 상태 아님.

- **적이 이미 처치된 후 다른 적의 DOT 피해**: 처치 판정은 즉시 발생. 이미 `current_hp=0`인 유닛은 DOT 처리 대상에서 제외.

- **스킬 선택 후 SP가 cost 미만인 경우** (버그): UI가 비활성화로 방지. 만약 호출되면 기본 공격으로 대체 + `push_warning`.

- **전투 중 앱 백그라운드 전환**: 입력 대기 상태 유지. (2026-07-26 리비전 — 정정: 브라우저가 비활성 탭에서 requestAnimationFrame 호출을 정지시켜 Godot의 프레임 콜백 자체가 호출되지 않는 것이지, Godot 자체의 pause 메커니즘이 작동하는 것이 아니다 — `씬-관리.md`/`전투-공식.md`에서 이미 확인된 메커니즘과 동일.) 재활성화 시 입력 대기 화면 그대로 복귀.

## Acceptance Criteria

1. (턴 순서, 2026-07-26 리비전 — 구성 명시) GIVEN 유닛 5개: spd9-동료A, spd8-동료B, spd8-적C, spd6-동료D, spd2-적E (파티 인덱스 A<B<D 순) WHEN `#6 공식③`으로 턴 순서를 계산하면 THEN 진행 순서는 [A(9), B(8, 동료 우선), C(8), D(6), E(2)]이다.

2. (플레이어 입력) GIVEN 플레이어 동료 턴 WHEN 기본 공격 + 적 타겟 선택 THEN 데미지가 계산·적용되고 해당 적 HP가 감소한다.

2b. (장비 반영, 2026-07-28 추가 — 교차 리뷰에서 발견된 미연결 문제 검증) GIVEN 동료 base_atk=10이고 weapon_slot에 ATK+3 장비가 장착된 상태에서 WHEN 전투가 시작되면 THEN 이 동료의 전투용 atk는 13(`#4.get_effective_atk()` 반영)이고, 이후 이 동료가 기본 공격을 실행하면 `#6 공식①`에 base_atk=10이 아닌 13이 입력값으로 전달된다.

2c. (회복 스킬 실행, 2026-07-28 추가 — 재검토에서 발견된 미구현 회복 경로 검증) GIVEN 지원형 동료가 `target_type="ally"`, `heal_multiplier=0.3`인 스킬을 아군 대상(base_hp=80, current_hp=40)에게 사용하는 상태에서 WHEN 액션이 실행되면 THEN `#6 공식⑥`이 호출되어 대상의 current_hp가 64로 갱신된다 (데미지 공식이 아닌 회복 공식이 호출됨).

3. (스킬 SP 체크) GIVEN SP=1, cost_sp=2인 스킬이 있는 턴 WHEN 스킬 버튼 표시 THEN 버튼이 비활성화되어 있다.

4. (적 AI 위임, 2026-07-26 리비전 — targeted_this_turn 검증 추가) GIVEN 적 유닛 턴이고 `targeted_this_turn`에 이미 동료 X가 포함된 상태에서 WHEN AI가 호출되면 THEN `decide_action(enemy, alive_companions, targeted_this_turn)`이 현재 `targeted_this_turn` 값을 인자로 전달받아 호출되고, #7 AI가 반환한 (액션, 타겟)으로 자동 실행되며, 반환된 타겟이 `targeted_this_turn`에 추가된다.

4b. (라운드 시작 시 초기화, 2026-07-26 추가) GIVEN 라운드 1이 종료되고 `targeted_this_turn`에 값이 남아있는 상태에서 WHEN `on_round_start()`가 실행되면(라운드 2 시작) THEN `targeted_this_turn`이 빈 배열로 초기화된다.

5. (DOT 즉사 → 전투 종료) GIVEN 마지막 적 HP=3이고 poison(5)이 활성인 상태에서 WHEN 해당 적 턴 DOT 틱 처리 후 `#6 공식⑤`를 호출하면 THEN victory가 반환되고 이 시스템이 전투 종료(승리) 처리를 트리거한다.

6. (승리 확정 순서, 2026-07-26 리비전 — #6 AC9와 일치하도록 재작성) GIVEN 마지막 적과 마지막 동료가 같은 턴에 모두 전투불능에 이를 수 있는 상황에서 WHEN `#1`이 "공격자 피해 → 방어자 피해" 고정 순서로 `#6 공식⑤`를 호출하면 THEN 마지막 적의 HP가 먼저 0이 되어 victory가 반환되고, 그 이후 처리되는 반격 데미지는 이 판정에 영향을 주지 않는다. (이것은 우선순위 규칙이 아니라 고정된 적용 순서의 결과 — `#6` AC9 참조.)

7. (SP 회복 타이밍) GIVEN sp=1, cost_sp=2인 유닛이 기본 공격 후 WHEN 턴 종료 시 THEN sp=2가 되어 다음 턴에 스킬 사용 가능하다.

8. (패배) GIVEN 모든 동료 current_hp=0인 상태에서 WHEN `#6 공식⑤`가 defeat을 반환하면 THEN `RunManager.end_run(success=false)`가 호출된다.
