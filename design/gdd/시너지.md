## Overview

시너지 시스템은 파티에 편성된 동료들의 `class_type` 조합(또는 특정 동료 쌍)을 판별해 자동으로 ATK 보너스를 부여하는 Gameplay 레이어 시스템이다. 전투 시작 전, 파티 편성이 확정되는 시점에 어떤 시너지가 활성화되는지 결정되며 전투 중에는 값이 고정된다(#6 전투 공식의 결정론적 계산 원칙과 동일 — 크리티컬/회피 없는 전투에 확률 요소를 끼워 넣지 않는다). 플레이어가 별도로 발동하거나 선택하는 액션이 아니라, "이 조합을 짰더니 강해졌다"를 전투 결과로 발견하게 만드는 순수 규칙/데이터 계층이다.

시너지 규칙 테이블은 동료 수(N)에 독립적으로 확장 가능한 구조로 설계한다 — MVP는 동료 4명(class_type 4종 고정 태그: tank/dealer/balance/support)만 존재하지만, Vertical Slice에서 로스터가 10명으로 늘어나도 이 GDD가 정의하는 규칙 형식(조합 조건 → ATK 보너스)만 확장하면 되고 구조 자체는 바뀌지 않는다. 보너스는 `#6 전투 공식`이 이미 가정해 둔 인터페이스(공식① "수정된 atk 입력")만 사용한다 — 스킬 배율·방어력·속도 등 다른 스탯에는 개입하지 않는다.

플레이어 입장에서는 파티 선택 화면(`#15`)에서 조합을 짜다가 특정 동료들을 같이 넣었을 때 뭔가 다르다는 걸 확인하고, 실제 전투에서 그 조합이 유독 강하다는 걸 체감한다. 이 발견이 `game-concept.md`의 Core Dynamics "이 파티 조합이 개사기다"를 발견하는 행동 그 자체다.

## Player Fantasy

플레이어가 원하는 감정: **"내가 발견한, 나만의 필승 조합."** 특정 타입/역할 조합이 만드는 예상 밖의 강함을 발견했을 때의 쾌감 — 공략집을 본 게 아니라 직접 짜보다가 우연히 혹은 의도적으로 알아챘다는 자부심이다.

시너지는 파티 선택 화면(`#15`)에서 "이 조합, 뭔가 있을 것 같다"는 예감으로 시작해서, 실제 전투에서 예상보다 데미지가 세게 들어갈 때 "역시!"로 확인된다. `#8`은 UI를 소유하지 않고 별도의 큰 배너나 팝업으로 시너지를 광고하지 않는다 — HUD에 찍히는 데미지 수치만으로 플레이어가 스스로 "이 조합이 유독 세다"를 알아채게 만드는 것이 핵심이다. 노골적으로 알려주는 순간 "발견"이 아니라 "안내"가 되어버린다.

이건 `game-concept.md` Pillar 4 "전략은 단순하게, 조합은 깊게"를 수치로 구현하는 지점이다 — 개별 전투 공식(①②③)은 단순하지만 "어떤 `class_type` 조합을 짜느냐"는 파고들수록 깊어진다. Core Dynamics의 "이 파티 조합이 개사기다"를 플레이어가 커뮤니티에 공유하게 되는 행동의 직접적 원천이 바로 이 시스템이다.

레퍼런스: 포켓몬 타입 상성 조합, TFT류의 "시너지 발견" 쾌감 — 다만 이 게임은 UI로 시너지를 대놓고 알려주지 않는 은은한 방식을 택한다(발동 방식 결정과 일관됨).

> lean 모드 — 이 섹션은 `creative-director` 상담 없이 작성. 필요 시 나중에 검토 요청 가능.

## Detailed Design

### Core Rules

1. **판별 단위**: 파티에 존재하는 `class_type`들의 순서 없는 쌍(unordered pair) — 예: `(tank, support)`. 규칙 테이블은 `(class_type_a, class_type_b) → atk_bonus`(flat 가산치) 형태의 데이터로 정의한다. MVP는 6개 쌍(tank-dealer, tank-balance, tank-support, dealer-balance, dealer-support, balance-support) 전부를 큐레이션한다. 정확한 가산치는 Formulas 섹션에서 확정.
2. **동시 발동 및 스택**: 파티(최대 3명)에 존재하는 모든 성립 쌍의 보너스를 전부 더한다. 예: 3명이 서로 다른 타입이면 최대 3개 쌍이 동시 성립 — 각 쌍의 flat 보너스를 합산한 값이 최종 시너지 보너스.
3. **적용 대상**: 팀 단위로 계산된 `synergy_bonus`(위 공식)를 기준으로, 각 파티원은 자신의 `base_atk`의 50%를 상한으로 이 값을 가산받는다(`applied_bonus = min(synergy_bonus, floori(base_atk * 0.5))`) — 특정 역할만 받는 게 아니라 파티원 전원이 같은 규칙으로 받되, 저스탯 캐릭터가 고스탯 캐릭터와 똑같은 flat 값을 받을 때 상대 증가율이 과도해지는 것을 막기 위한 개별 상한이다(2026-08-08 리비전 — 독립 검토에서 발견, 아래 근거 참조).
4. **계산 시점과 고정**: 파티 편성이 확정되는 시점(전투 진입 직전, `#1 턴제 전투`의 유닛 구성 단계)에 정확히 1회 계산되고, 전투가 끝날 때까지 값이 변하지 않는다. 전투 중 파티원이 전투불능 상태가 되어도 그 파티원이 속한 쌍의 보너스는 계속 유지된다 — 재계산하지 않는다(#6 전투 공식의 결정론적 계산 원칙과 일관, 매 히트마다 "지금도 이 조합이 유효한가"를 재확인하는 복잡도를 만들지 않음).
5. **동일 `class_type` 중복 파티원**: MVP는 타입당 동료가 1명뿐이라 발생하지 않지만, 로스터가 확장되어 같은 타입 동료 2명이 함께 편성되면 그 조합도 규칙 테이블의 한 항목(`(tank, tank)` 형태)일 뿐이다 — 별도 특수 케이스 코드 없이 동일한 테이블 조회 로직으로 처리된다(N명 확장 요구사항을 만족시키는 지점).

## Formulas

### 시너지 보너스 (Synergy Bonus)

시너지 보너스 공식은 다음과 같이 정의된다:

`synergy_bonus = Σ SynergyTable[pair]` — **파티에 존재하는 서로 다른 `class_type`들의 집합에서 뽑은** 모든 성립 `(class_type_a, class_type_b)` 쌍에 대해 합산한다(같은 타입 동료가 여러 명이어도 "실제 동료 쌍의 개수"가 아니라 "성립하는 서로 다른 타입 쌍의 종류" 기준 — Edge Cases 참조. 이 공식 표기 자체가 "동료 쌍"이 아니라 "타입 쌍" 기준임을 명확히 하기 위해 2026-08-08 리비전에서 표현을 보강함).

`applied_bonus(unit) = min(synergy_bonus, floori(unit.base_atk * 0.5))` — **개인별 상한(2026-08-08 리비전 추가)**. 팀 전체 `synergy_bonus`는 하나의 값으로 계산되지만, 각 파티원에게 실제로 가산되는 값은 그 파티원 자신의 `base_atk`의 50%를 넘지 않는다.

`effective_atk = base_atk + weapon_bonus + applied_bonus(unit) + status_modifier`

**변수:**

| 변수 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `base_atk` | int | 10~30 | 동료 레지스트리 기본 ATK (`#10`) |
| `weapon_bonus` | int | 기존 `#4 장비` 정의값 | 장비 가산치 |
| `synergy_bonus` | int | 0~11 (MVP 6쌍 기준) | 파티 내 성립 `class_type` 쌍 보너스 합(팀 단위 값), 전투 시작 시 1회 계산 후 고정 |
| `applied_bonus(unit)` | int | 0~min(synergy_bonus, floori(base_atk\*0.5)) | 개별 파티원에게 실제로 가산되는 값 — 자신의 `base_atk` 50% 상한 적용 후 |
| `status_modifier` | int | 기존 `#12 상태이상` 정의값 | 상태이상 가산치 |
| `effective_atk` | int | 실질 10~41 (MVP 기준, 상한 미적용 시 이론값) | 공식①②의 `atk` 입력값 |

**개인별 상한(50%)을 추가한 근거 (2026-08-08 독립 /design-review, systems-designer 발견 → creative-director 채택)**: 원안은 `synergy_bonus`를 모든 파티원에게 동일한 flat 값으로 가산했는데, MVP 실제 동료 스탯(`base_atk`: tank=12, balance=18, dealer=28, support=14)에 최댓값 시나리오(`synergy_bonus=11`)를 대입하면 파티원마다 상대 증가율이 극단적으로 갈렸다 — dealer는 28→39(+39%)로 온건하지만, **같은 파티의 tank는 12→23로 +91.7%**, Tuning Knobs가 "로스터 확장 시" 우려로 미뤄뒀던 "+110%" 수준이 실제로는 MVP 데이터로 이미 재현 가능했다(원안의 Worked Example이 dealer만 예시로 들어 이 문제를 가려왔음). 50% 상한 적용 시: tank는 min(11, floori(12\*0.5)=6)=**6**(12→18, +50%), support는 min(11, 7)=**7**(14→21, +50%), balance는 min(11, 9)=**9**(18→27, +50%), dealer는 min(11, 14)=**11**(28→39, +39%, 상한 미적용 — 원안 그대로 유지). 결과: 시너지의 팀 단위 전략성(어떤 조합을 짤지)은 그대로 유지하면서, 개별 유닛이 자기 스탯 대비 비상식적으로 튀어오르는 걸 막는다.

**MVP `SynergyTable`(6쌍 전부 큐레이션, 저작 세션 systems-designer 자체 점검 완료 — 표 값 자체는 2026-08-08 독립 재검토에서도 문제 없음 확인, 개인별 상한은 별도 추가):**

| 쌍 | `atk_bonus` | 근거 |
|------|------|------|
| dealer–support | **+5** | 서포터가 딜러 화력을 증폭한다는 전형적 판타지 — 6쌍 중 최댓값으로 "화력 특화 조합" 정체성 |
| tank–dealer | **+4** | 탱커가 어그로 흡수 → 딜러 안전 극딜, 가장 직관적인 "탱딜" 조합이라 체감치 높게 |
| dealer–balance | **+3** | 밸런스형이 딜러 스킬 운용 보조 — 중간값 |
| balance–support | **+3** | 안정적 서포트 조합, 공격보다 지속력 쪽 시너지라 중간값 |
| tank–support | **+2** | 생존 위주 조합, 방어형끼리라 공격 보너스는 부차적 |
| tank–balance | **+2** | 방어 축 조합, 공격 임팩트 최소 |

`base_atk` 범위(10~30, 폭 20) 대비 단일 쌍 +2~+5는 저스탯 캐릭터 기준 7~50%p, 고스탯 캐릭터 기준 7~17%p — 체감되지만 스킬 배율(최대 2.0배)에 압도되지 않는 크기.

**Output Range**: 팀 단위 `synergy_bonus` 0~11 (MVP 6쌍 기준, 이 값 자체엔 클램핑 없음 — 로스터 확장 시 표에 없는 쌍은 0으로 처리). 개인별 `applied_bonus`는 위 50% 상한 적용 후 0~14(MVP 최고 `base_atk`인 dealer 28 기준 상한).

**검증(최댓값 시나리오, 3인 파티 서로 다른 타입 3종) — 팀 단위 `synergy_bonus`:**

| 파티 구성 | 성립 쌍 | 합산 `synergy_bonus` |
|------|------|------|
| tank+dealer+support | td(4)+ts(2)+ds(5) | **11 (최댓값)** |
| dealer+balance+support | db(3)+ds(5)+bs(3) | **11 (최댓값)** |
| tank+dealer+balance | td(4)+tb(2)+db(3) | 9 |
| tank+balance+support | tb(2)+ts(2)+bs(3) | 7 |

**Example — 파티(tank+dealer+support), `synergy_bonus=11`, 파티원별 개인 상한(50%) 적용 결과 (2026-08-08 리비전 — 원안은 dealer만 예시로 들어 실제로는 가장 온건한 사례였음, 이번 리비전에서 파티원 전원을 명시):**

| 파티원 | `base_atk` | 50% 상한 | `applied_bonus` | `effective_atk` | 스킬 데미지(배율1.8, 보스 def=8) | 시너지 無 대비 |
|--------|-----------|----------|------------------|------------------|-------------------------------|----------------|
| dealer | 28 | 14 | 11 (상한 미적용) | 39 | `floor(39×1.8)−8=62` | 42 → 62 (+48%) |
| tank | 12 | 6 | **6 (상한 적용, 원안이면 11)** | 18 | `floor(18×1.8)−8=24` | `floor(12×1.8)-8=13` → 24 (+85%, 원안 기준 154%보다 완화) |
| support | 14 | 7 | **7 (상한 적용, 원안이면 11)** | 21 | `floor(21×1.8)−8=30` | `floor(14×1.8)-8=17` → 30 (+76%) |

보스 처치 라운드가 줄어들되 원턴킬은 아님 — 전략 깊이는 유지되고, 저스탯 파티원의 극단적 상대 증가율은 50% 상한으로 완화됨.

**솔로 전투 무관 확인**: 시너지는 서로 다른 `class_type` 2인 이상 필요 — 솔로 런(첫 런 강제 솔로 보스전 포함)은 100% 영향 없음, 2026-08-02 보스 밸런스 튜닝과 충돌 없음.

## Edge Cases

- **파티가 1명뿐이거나(솔로 런 포함) 0명(호출 자체가 비정상이지만 방어적으로)인 경우**: 성립 가능한 쌍이 없으므로 `synergy_bonus = 0`이고 `applied_bonus`도 0. 별도 분기 없이 빈 합(empty sum)으로 자연스럽게 0이 됨(2026-08-08 리비전 — 0명 케이스도 동일 로직으로 커버됨을 명시, qa-lead 지적).
- **개인별 50% 상한과 다른 Edge Case의 상호작용**: 상한은 `unit.base_atk`(고정값, `#10` 레지스트리 값)만을 기준으로 계산되므로, 전투불능(사망) 여부나 장비/상태이상 수정치와 무관하게 항상 동일하게 적용된다 — 별도 처리 불필요.
- **파티에 서로 다른 `class_type`이 1종류뿐인 경우** (로스터 확장 후 같은 타입 동료로만 파티를 짠 경우): 판별은 **서로 다른 `class_type`의 개수**를 먼저 센 뒤 그 집합에서 쌍을 뽑는다 — 같은 타입 동료가 몇 명이든 "구별되는 타입 종류"가 1개면 쌍 자체가 성립하지 않아 `synergy_bonus = 0`.
- **같은 타입 조합이 여러 동료 쌍으로 실현되는 경우** (예: tank 2명 + dealer 1명 → 실제 동료 쌍은 (tank1,dealer1), (tank2,dealer1) 2개): `tank-dealer` 보너스는 **한 번만** 적용된다 — 실제 동료 쌍 개수가 아니라 "성립하는 서로 다른 `class_type` 쌍의 종류" 기준으로 계산하므로 중복 가산되지 않는다.
- **`SynergyTable`에 정의되지 않은 쌍**: 보너스 0으로 처리(로스터 확장 시 아직 값을 정하지 않은 조합의 기본 동작). `push_warning` 없음 — 데이터 오류가 아니라 "아직 의도적으로 정의하지 않은 조합"이 정상 상태이기 때문(모든 조합을 강제로 채워야 한다는 요구사항 없음).
- **전투 중 파티원이 전투불능(사망) 상태가 되는 경우**: Core Rule 4에서 확정된 대로 `synergy_bonus`는 재계산하지 않고 전투 시작 시 값을 그대로 유지한다.
- **장비/상태이상 수정치와의 연산 순서**: `synergy_bonus`·`weapon_bonus`·`status_modifier` 모두 flat 가산이므로 연산 순서와 무관(교환법칙) — `#1 턴제 전투`가 어떤 순서로 더해도 `effective_atk` 결과는 동일하다.

## Visual/Audio Requirements

이 시스템은 자체 시각/오디오 자산을 소유하지 않는다. `Player Fantasy` 섹션에서 확정한 대로, 시너지는 별도 배너·팝업·아이콘으로 광고되지 않는다 — 상승한 데미지 수치가 `#20 UI/HUD`의 기존 데미지 팝업/HP 바에 자연스럽게 반영되는 것이 유일한 표현 방식이다. 이후 세션에서 "노골적으로 안 보여준다"는 결정 자체를 뒤집기로 하면(예: 파티 선택 화면에 "시너지 활성" 뱃지 추가), 그건 이 GDD의 재설계가 아니라 `#15 파티 구성`/`#20 UI/HUD` 쪽의 UI 추가 기능으로 다뤄야 한다.

**개발자 전용 검증 로그 (2026-08-08 리비전 추가 — 독립 검토에서 발견된 "무언 발견" 검증 공백 해결, 사용자 결정)**: 플레이어에게는 여전히 UI를 노출하지 않지만, `get_applied_synergy_bonus()`가 0이 아닌 값을 반환할 때마다 `push_warning`이 아닌 일반 로그(`print` 또는 프로젝트 표준 디버그 로거)로 `"[Synergy] {party 구성} → team={synergy_bonus}, applied={unit_id}:{applied_bonus}"` 형태를 남긴다(빌드 시 스트립 가능한 디버그 전용, 릴리즈 성능/노출에 영향 없음). 이 로그가 "노골적으로 안 보여준다" 철학을 깨지 않으면서 개발자가 실제 플레이 중 시너지가 의도대로 발동하는지 확인할 수 있는 유일한 관측 수단이 된다. **셀프 플레이테스트 체크리스트 항목 1개 추가**(`production/qa/` 또는 세션 상태에 기록): "다양한 파티 조합으로 최소 3회 이상 플레이하며 이 로그를 직접 확인 — 데미지 수치 변화를 로그 없이도 알아챌 수 있었는지 별도로 기록." 이것이 Open Questions #3(아래에서 결정으로 전환됨)이 요구하던 실질적 검증 트리거다.

## Acceptance Criteria

1. GIVEN 파티에 서로 다른 class_type 2종(tank, dealer)만 있을 때, WHEN 전투가 시작되면, THEN `synergy_bonus`는 정확히 tank-dealer 쌍의 값(+4)이고 다른 쌍은 0이다.
2. GIVEN 파티에 서로 다른 class_type 3종(tank, dealer, support)이 있을 때, WHEN 전투가 시작되면, THEN `synergy_bonus`는 3쌍(td+ts+ds = 4+2+5) 합산인 11이다.
3. GIVEN 파티에 balance가 포함된 조합(예: dealer+balance)이 있을 때, WHEN 전투가 시작되면, THEN `synergy_bonus`는 dealer-balance 쌍의 값(+3)이다. (`SynergyTable` 6쌍 중 balance 관련 쌍 커버리지 확보)
4. GIVEN 파티가 동료 1명뿐일 때(솔로 런 포함), WHEN 전투가 시작되면, THEN `synergy_bonus`는 0이다.
5. GIVEN 파티에 같은 class_type 동료만 있어 서로 다른 타입이 1종류뿐일 때, WHEN 전투가 시작되면, THEN `synergy_bonus`는 0이다(성립 쌍 없음). **(MVP 로스터는 타입당 동료 1명뿐이라 이 시나리오는 실제 MVP 파티로는 구성 불가능 — AC9와 동일한 사유로, 합성 `companion_ids` 입력을 직접 넣는 단위 테스트로 검증한다. 2026-08-08 리비전 — qa-lead 지적, AC9와 같은 캐비어트 누락 발견.)**
6. GIVEN 파티에 tank 2명 + dealer 1명이 있을 때(같은 타입쌍이 실제 동료쌍 2개로 실현), WHEN `synergy_bonus`를 계산하면, THEN tank-dealer 보너스(+4)는 정확히 1회만 적용된다(중복 가산 없음). **(AC5와 동일한 사유로 합성 입력 단위 테스트 대상 — 2026-08-08 리비전.)**
7. GIVEN 파티 편성 순서가 [dealer, tank]인 경우와 [tank, dealer]인 경우, WHEN 각각 `synergy_bonus`를 계산하면, THEN 두 결과는 동일하다(순서 무관 — unordered pair 검증).
8. GIVEN `synergy_bonus`가 전투 시작 시 계산된 상태에서, WHEN 전투 중 한 파티원이 데미지로 `current_hp=0`(전투불능)에 도달하면, THEN 그 시점 이후 조회한 `synergy_bonus` 값은 전투 시작 시 계산된 값과 동일하다(재계산 없음 — 전투불능 처리 전후로 값을 직접 조회·비교해 검증).
9. GIVEN `SynergyTable`에 정의되지 않은 임의의 `class_type` 쌍 키로 직접 조회하면, WHEN 조회 함수를 호출하면, THEN 기본값 0을 반환하고 경고를 출력하지 않는다. (MVP는 class_type이 4종뿐이라 6쌍이 전부 정의됨 — 이 AC는 게임플레이 시나리오가 아니라 `SynergyTable` 조회 함수 자체의 단위 테스트로 검증하며, 로스터 확장으로 5번째 class_type이 추가된 뒤에야 실제 게임플레이로도 재현 가능해진다.)
10. GIVEN dealer(`base_atk=28`), `synergy_bonus=11`(team 단위), WHEN `get_applied_synergy_bonus`로 dealer 개인값을 구하면, THEN `min(11, floori(28*0.5)=14)=11`(상한 미적용)이고, `weapon_bonus=0`/`status_modifier=0`일 때 `effective_atk`는 39이다.
11. **(신규, 2026-08-08 — qa-lead 지적, 통합 계약 미검증 발견)** GIVEN tank(`base_atk=12`)가 `synergy_bonus=11`인 파티에 속할 때, WHEN `get_applied_synergy_bonus(companion_ids, 12)`를 호출하면, THEN 50% 상한이 적용되어 `min(11, floori(12*0.5)=6)=6`을 반환한다(원안이었다면 11 — 상한이 실제로 걸리는 경계값 케이스를 검증).
12. **(신규, 2026-08-08 — qa-lead 지적)** GIVEN 전투가 시작될 때, WHEN `#1 턴제 전투`의 유닛 구성 단계가 실행되면, THEN 파티원 각각에 대해 `get_applied_synergy_bonus()`가 정확히 1회씩 호출되고 그 반환값이 해당 유닛의 `effective_atk` 계산에 그대로(변형 없이) 포함된다 — spy/mock으로 호출 횟수와 전달값을 검증하며, 손으로 계산한 기대 `effective_atk`와의 비교만으로는 대체할 수 없다(호출 누락·중복 호출·매 턴 재호출 같은 배선 실수는 AC1-11만으로는 잡히지 않음).
