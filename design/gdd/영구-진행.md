# 영구 진행 (Permanent Progression)

> **Status**: In Design
> **Author**: 사용자 + Claude Code
> **Last Updated**: 2026-07-26
> **Implements Pillar**: 성장은 영원하다
> **Creative Director Review**: Skipped — Lean 모드

## Overview

영구 진행 시스템은 런과 런 사이에 **영속되는 플레이어 진행 상황** — 해금된 동료 목록과 최고 층수 기록 — 을 소유하고 관리하는 Progression 레이어 시스템이다. 런이 종료되면 #13 런 상태 관리로부터 "이번 런 발견 동료 목록"을 받아 해금 처리를 수행하고, #17 로컬 세이브를 통해 디스크에 기록한다. 게임 시작 시에는 로컬 세이브에서 복원해 #15 파티 구성 등 소비 시스템에 "현재 사용 가능한 동료 목록"을 제공한다. 이 시스템은 필라 2("성장은 영원하다")의 기술적 실현체로, 런이 실패해도 발견한 동료는 반드시 남는다는 약속을 보장한다.

## Player Fantasy

"이 런 실패했지만 ○○는 해금됐다."

런 결과 화면에서 새 동료 카드가 펼쳐지는 순간 — 그 "그래도 얻었다"는 감각이 이 시스템이 만드는 전부다. 런이 끝날 때마다 뭔가 남는다는 확신이 다음 런을 시작하게 만든다.

반대로 이 시스템이 실패하면: 해금했던 동료가 다음 게임 세션에 없다. #17 로컬 세이브와 함께 "신뢰"가 깨지는 가장 치명적인 버그 유형이다.

## Detailed Rules

### 소유 데이터

```gdscript
# ProgressManager Autoload (또는 RunManager와 통합 고려 — Open Questions 참조)

var unlocked_companions: Array[String] = []  # companion id 목록
var highest_floor_reached: int = 0
```

MVP에서 영구 진행 데이터는 이 두 필드가 전부다. 경험치·레벨·골드·업그레이드는 YAGNI.

### 초기화 (게임 시작 시)

```
1. #17 로컬 세이브 → load_section("companion_unlocks") → unlocked_companions 복원
2. #17 로컬 세이브 → load_section("floor_reached") → highest_floor_reached 복원
3. No Save Found 상태: unlocked_companions = [BASE_COMPANION_ID], highest_floor_reached = 0
4. (2026-07-26 추가) 복원된 unlocked_companions의 각 id에 대해 `#10 동료 데이터`에서 존재 확인 —
   존재하지 않는 id(예: BASE_COMPANION_ID 확정 전 임시값으로 저장된 구 세이브)는
   `push_warning("Unknown unlocked companion id on load: [id]")` 후 목록에서 제거.
   discovered_companions 처리 시 이미 쓰는 것과 동일한 검증을 로드 시점에도 적용 —
   BASE_COMPANION_ID 확정 시 세이브 호환성 문제를 여기서 조기에 잡는다.
```

`BASE_COMPANION_ID`: 기본 동료 1명 고정 상수 (예: `"warrior_base_01"`). 이 ID는 항상 해금 상태로 시작.

### 런 종료 시 처리 (`commit_run_end(discovered_ids: Array[String], floor: int)`, 2026-07-26 리비전 — 배치 커밋으로 재작성)

**리비전 사유**: 기존 버전은 `unlock_companion()` 호출마다 즉시 저장 + 루프 뒤 별도 `save()` + `update_highest_floor()`도 자체 즉시 저장 — 세 갈래의 저장 호출이 서로 모순되며, 실제로는 다중 발견 시 여러 번의 중복 저장이 발생하거나(비효율) 첫 저장 실패 시 나머지 배치가 통째로 유실될 위험이 있었다(리뷰에서 발견). 아래 단일 트랜잭션으로 대체:

```
commit_run_end(discovered_ids, floor):
  newly_unlocked: Array[String] = []
  for id in discovered_ids:
    if not #10.exists(id):
      push_warning("Unknown companion id: [id]")
      continue
    if id not in unlocked_companions:
      unlocked_companions.append(id)   # 메모리 변경만 — 저장 없음
      newly_unlocked.append(id)
  if floor > highest_floor_reached:
    highest_floor_reached = floor      # 메모리 변경만 — 저장 없음
  save_result = await #17.save_section("companion_unlocks", unlocked_companions)
              + await #17.save_section("floor_reached", highest_floor_reached)  # 단일 트랜잭션, 한 번만 저장
  if save_result.success:
    for id in newly_unlocked: emit companion_unlocked(id)
    if floor > (floor 갱신 전 값): emit highest_floor_updated(floor)
    emit progress_committed(newly_unlocked, save_result.success)
  else:
    emit progress_committed(newly_unlocked, save_result.success)  # 실패해도 신호는 발신 — RunManager가 대기 해제 가능해야 함
  return newly_unlocked
```

**`#13 런 상태 관리`는 `progress_committed` 신호를 받은 뒤에만 RunResultScreen으로 전환한다** (Core Rule 2 참조) — 저장 성공/실패와 무관하게 신호가 발신되므로, 최악의 경우(16500ms 저장 실패)에도 화면이 영원히 멈추지 않는다.

### 핵심 API

| 메서드 | 입력 | 출력 | 설명 |
|--------|------|------|------|
| `commit_run_end(discovered_ids, floor)` | Array[String], int | Array[String] (신규 해금 id 목록) | **런 종료 시 유일한 진입점** — 배치 처리 + 단일 저장 + 신호 발신 |
| `unlock_companion(id)` | String | void | 목록 추가 + 즉시 저장. **런 종료 경로에서는 사용하지 않음** — `#3 동료 해금`의 디버그/단독 호출 등 배치 밖 시나리오 전용 내부 헬퍼 |
| `is_unlocked(id)` | String | bool | 해금 여부 조회 |
| `get_unlocked_companions()` | — | Array[String] | 전체 해금 목록 반환 |
| `update_highest_floor(floor)` | int | void | 더 높으면 갱신 + 즉시 저장. `unlock_companion()`과 동일하게 배치 밖 전용 |

### Core Rules

1. **해금은 단방향**: 한 번 해금된 동료는 절대 잠금 해제 불가. `unlocked_companions`에서 제거 없음.
2. **런 종료는 배치 커밋, 화면 전환은 신호 대기 (2026-07-26 리비전)**: 런 종료 시 해금·최고 층수 갱신은 `commit_run_end()` 하나로 처리되며 저장도 단 한 번만 발생한다. `#13`은 `progress_committed` 신호를 받을 때까지 RunResultScreen 전환을 대기한다 — "화면 표시 전에 저장 완료"가 실제로 강제된다(이전 버전은 이 대기를 명시하지 않아 미보장이었음). `unlock_companion()`/`update_highest_floor()`의 개별 "즉시 저장"은 배치 밖(디버그 등) 호출에만 적용된다.
3. **기본 동료는 항상 해금**: 초기화 시 `BASE_COMPANION_ID`가 목록에 없으면 추가. 로컬 세이브 손상·초기화 후에도 기본 동료는 복구.
4. **#17 저장 실패 시 메모리 상태 유지**: 저장 실패해도 이번 세션의 `unlocked_companions`는 메모리에 유지 — 게임을 계속 진행할 수 있다. 단, 세션 종료 시 소실. UI에 "저장 실패" 알림 (#17 로컬 세이브가 신호 발신). `commit_run_end()`는 저장 실패 시에도 `progress_committed(success=false)`를 발신해 `#13`이 무한 대기하지 않도록 한다.

### Signals (2026-07-26 추가 — 리뷰에서 발견된 미정의 갭)

```gdscript
signal companion_unlocked(id: String)
signal highest_floor_updated(floor: int)
signal progress_committed(newly_unlocked: Array[String], save_success: bool)
```

## Formulas

수치 공식 없음. 이 시스템의 "공식"은 아래 두 조건이다.

**해금 조건:**
```
unlock_companion(id) 실행 조건:
  id in RunManager.discovered_companions
  AND id not in unlocked_companions
```

**최고 기록 갱신 조건:**
```
update_highest_floor(floor) 실행 조건:
  floor > highest_floor_reached
```

## Edge Cases

- **같은 런에서 이미 해금된 동료를 다시 발견**: `is_unlocked(id) == true` → `unlock_companion()` 미호출. `#3 동료 해금`이 "이미 동료가 되어 있어요" 처리.

- **#17 저장 실패 후 게임 재시작**: 저장 직전까지의 상태만 복원됨 — 저장 실패한 런의 해금은 소실. 저장 실패 UI는 #17가 표시하므로 플레이어는 인지한 상태. 이 시스템은 "복구 재시도" 없음 — 책임은 #17 소유.

- **`unlocked_companions`가 비어 있는 세이브 파일 로드**: 손상 또는 비정상 데이터. Core Rule 3에 따라 `BASE_COMPANION_ID` 강제 추가 후 진행.

- **`discovered_companions`에 존재하지 않는 companion_id 포함**: `#10 동료 데이터`에서 해당 id 조회 실패 → `unlock_companion()` 미호출 + `push_warning("Unknown companion id: [id]")`. 유효하지 않은 id는 조용히 무시하지 않고 경고 기록.

- **최고 층수 0층 (런 실패, 1층도 못 깨고 전멸)**: `run_floor = 1`이 전달됨 (1층에 진입했으므로). `highest_floor_reached`는 0→1로 갱신. "1층 클리어" 기록이 아닌 "1층 도달" 기록.

## Acceptance Criteria

1. (초기화 – 신규) GIVEN 로컬 세이브가 없는 상태에서 WHEN 게임이 시작되면 THEN `unlocked_companions = [BASE_COMPANION_ID]`이고 `highest_floor_reached = 0`이다.

2. (초기화 – 복원) GIVEN `companion_unlocks: ["warrior_base_01", "hidden_mage_02"]`가 저장된 세이브가 있을 때 WHEN 게임이 시작되면 THEN `unlocked_companions`에 두 id가 모두 복원된다.

3. (해금 – 기본 흐름) GIVEN `unlocked_companions = ["warrior_base_01"]`인 상태에서 WHEN `unlock_companion("hidden_mage_02")`가 호출되면 THEN `unlocked_companions = ["warrior_base_01", "hidden_mage_02"]`이고 `#17.save_section("companion_unlocks", ...)`이 올바른 인자로 호출된다. (실제 디스크 저장 완료 여부는 `#17`의 Integration 테스트 범위 — 이 AC는 #14가 저장 API를 올바르게 호출하는지만 검증한다.)

4. (해금 – 즉시 저장, **Integration** — 실제 `#17` 필요, mock 불가) GIVEN `unlock_companion("hidden_mage_02")`가 호출된 직후 WHEN 세션이 즉시 종료되면 THEN 다음 게임 시작 시 `"hidden_mage_02"`가 `unlocked_companions`에 있다.

5. (중복 해금 방지) GIVEN `unlocked_companions = ["warrior_base_01", "hidden_mage_02"]`인 상태에서 WHEN `unlock_companion("hidden_mage_02")`가 다시 호출되면 THEN `unlocked_companions`의 크기는 변하지 않는다 (중복 없음).

6. (최고 층수 갱신) GIVEN `highest_floor_reached = 2`인 상태에서 WHEN `update_highest_floor(3)`이 호출되면 THEN `highest_floor_reached = 3`이고 `#17.save_section("floor_reached", 3)`이 호출된다.

7. (최고 층수 미갱신) GIVEN `highest_floor_reached = 3`인 상태에서 WHEN `update_highest_floor(2)`가 호출되면 THEN `highest_floor_reached`는 3으로 유지된다.

8. (기본 동료 복구) GIVEN `unlocked_companions = []`인 손상 세이브가 복원된 상태에서 WHEN 초기화가 완료되면 THEN `unlocked_companions`에 `BASE_COMPANION_ID`가 포함된다.

9. (런 종료 배치 커밋, 2026-07-26 재작성) GIVEN 런이 종료되고 `discovered_companions = ["hidden_archer_03"]`, `run_floor=2`가 RunManager에서 전달될 때 WHEN `commit_run_end(["hidden_archer_03"], 2)`가 호출되면 THEN `unlocked_companions`와 `highest_floor_reached`가 메모리에서 모두 갱신된 뒤 `#17.save_section()`이 **정확히 2회**(각 섹션당 1회) 호출되고, 완료 시 `progress_committed(["hidden_archer_03"], true)`가 발신된다. (기존 버전은 다중 저장 호출 여부가 미정이었음 — 이 AC로 정확히 고정.)

9b. (다중 발견 배치, 2026-07-26 추가) GIVEN `discovered_companions = ["hidden_archer_03", "hidden_mage_02"]`가 전달될 때 WHEN `commit_run_end()`가 호출되면 THEN 두 id 모두 `unlocked_companions`에 추가되지만 `#17.save_section()`은 **여전히 섹션당 1회씩만** 호출된다 (id 개수와 무관하게 배치당 1회).

10. (유효하지 않은 id) GIVEN `discovered_companions = ["존재하지않는ID"]`가 전달될 때 WHEN 처리하면 THEN `push_warning`이 기록되고 `unlocked_companions`는 변하지 않으며 게임이 계속 진행된다.
